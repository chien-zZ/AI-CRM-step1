# 数据库与迁移基线

- 状态：架构边界已确认，命令和实现待工程初始化
- 适用范围：应用 PostgreSQL、Drizzle Schema、Repository、事务和迁移
- 架构依据：ADR-0011

## 开源与自研边界

- PostgreSQL、Drizzle ORM、Drizzle Kit 和批准的 PostgreSQL 驱动使用开源实现。
- `packages/database`、模块 Repository、Unit of Work、错误映射和迁移治理由项目自研。
- 自研部分只定义项目边界和运行规则，不复制数据库、ORM、驱动或连接池功能。

## 目录原则

- `packages/database`：连接、事务、迁移执行、健康检查和测试工具。
- `packages/platform-modules/<module>`：该平台模块私有的 Drizzle Schema、Repository 与映射器。
- `packages/domain-modules/<module>`：边界确认后，该领域模块私有的 Drizzle Schema、Repository 与映射器。
- `scripts/migration`：迁移校验、执行、回填和恢复辅助工具。

不得建立汇总全部业务表的公共导出，也不得从其他模块导入 Drizzle 表对象或 Repository。

## 每个数据库变更必须提供

1. 所有模块、变更目的和兼容的应用版本范围。
2. 经评审的 SQL 迁移和更新后的模块 Drizzle Schema。
3. 锁表、耗时、磁盘、连接和复制影响评估。
4. 旧版本应用与新结构并存时的兼容说明。
5. 回滚应用、前滚修复、数据恢复或备份点说明。
6. 数据回填的幂等、断点续跑、限速和进度观测方案。
7. 从空库及当前基线升级的迁移测试。

## 执行纪律

- 迁移必须是单独部署步骤，不随 API 或 Worker 启动自动运行。
- 迁移使用专用 DDL 凭据和全局互斥；应用运行时账号不拥有 DDL 权限。
- 已执行迁移不可修改，修复以新迁移追加。
- 共享环境禁止使用 `drizzle-kit push` 或自动 Schema 同步。
- 破坏性迁移先完成兼容代码、回填和读写切换，再在后续版本删除旧结构。
- 迁移失败时先判断应用兼容性和数据状态，不机械执行可能丢失新数据的 Down Migration。

## 上线前检查

- SQL 与执行计划已评审，Raw SQL 使用参数化输入。
- 备份或恢复点可用，恢复步骤已验证。
- 长事务、并发 DDL 和锁等待风险已在接近真实数据量的环境验证。
- 迁移、应用回滚和前滚修复的负责人及停止条件明确。
- 指标与告警能观察迁移状态、连接池、错误、死锁、慢查询和数据库容量。

## 已实现命令

根 `pnpm db:migrate` 是部署迁移入口。它组合 `packages/database/migrations` 与 `packages/platform-modules/*/migrations`，按全局十位版本号排序后在同一 advisory lock 下执行；模块目录发现顺序不能改变迁移顺序。模块自己的 `migrate` 命令只用于隔离开发与所有权测试。

- `DATABASE_MIGRATION_URL_FILE=<path> pnpm db:migrate`：使用专用迁移连接执行版本化 SQL。连接字符串只从文件读取，不接受命令行值。
- 迁移文件位于拥有包的 `migrations/`，名称为十位全局递增编号、下划线描述和 `.sql` 后缀；同名 `.meta.json` 必须记录 Owner、目的、兼容范围、锁与数据影响、回填、破坏性标记、恢复和前滚修复指导。破坏性迁移还必须记录明确批准。
- 执行器使用 PostgreSQL Advisory Lock，校验已执行迁移 Checksum，并仅在迁移事务成功后写入 `ai_crm_migrations.applied_migrations`。
- API 和 Worker 启动不得调用迁移命令；共享环境禁止 `drizzle-kit push`。
