# ADR-0014：自研通知中心与站内通知优先

- 状态：已接受
- 日期：2026-07-22
- 决策人：项目负责人
- 适用范围：`notifications`、站内通知、模板、偏好、渠道投递和工作台通知入口
- 依赖决策：ADR-0001、ADR-0003、ADR-0006、ADR-0007、ADR-0009、ADR-0010、ADR-0011、ADR-0013

## 已知事实

- 第一阶段已确认 PC Web、内部移动端和外部端三个应用入口；当前通知呈现和标准 Keycloak 登录 walking skeleton 只确认到 PC Web，另外两端的载体、认证和通知交互尚待评审。
- 业务模块、Workflow、Task Center、通知和外部渠道已经有明确职责边界。
- RabbitMQ、Outbox/Inbox、PostgreSQL、Redis 和版本化业务配置底座已经确认。
- 项目负责人确认自研通知中心，第一阶段仅实现站内通知与轮询，使用受限 Mustache 模板，外部渠道后续通过适配器接入。

## 允许的假设

- 第一阶段通知用户均可通过 PC Web 查看站内通知。
- 业务模块能够通过 `platform-sdk` 或可靠事件提交明确的通知意图。
- Worker 负责延迟生成、投递、重试、死信和回执处理。

## 禁止的假设

- 不从历史材料确认企微应用消息、微信订阅消息、短信、邮件、JPush、WebSocket 或移动端推送已经进入第一阶段。
- 不推断任何 CRM 通知类别、模板、收件角色、触发条件、优先级、免打扰规则或重试次数。
- 不把“通知已生成”“服务商已接收”“外部渠道已送达”和“用户已阅读”视为同一状态。
- 不把通知当作 Task、审批、SLA、预警处置或业务动作完成的事实源。
- 不允许通知模板执行 JavaScript、SQL、网络访问、任意 Helper 或未清洗 HTML。

## 决策

### 1. 通知中心控制面自研

`packages/platform-modules/notifications` 自研以下业务中立能力：

- 通知意图接收、幂等、收件人解析和实际收件人快照。
- 站内通知记录、未读/已读、归档和用户可见状态。
- 通知模板、变量 Schema、不可变版本和受控渲染。
- 用户通知偏好、免打扰和强制通知策略。
- 渠道地址、渠道投递、重试、回执、失败和人工重放。

选择自研的原因是通知必须与项目的人员、Assignment、授权、业务资源、Task Center、审计和 Outbox 语义结合。Novu 等开源通知平台可以提供多渠道工作流和模板管理，但也会引入独立用户、模板、工作流、存储和运行队列，与当前平台层重复。第一阶段渠道单一，自研小而明确的控制面更容易保持权限和事实源一致。

项目不自研消息代理、数据库、缓存、外部通信网络或服务商 API；通知中心复用 PostgreSQL、RabbitMQ、Redis 和后续官方渠道 SDK/协议。

### 2. 第一阶段只实现站内通知

- PostgreSQL 中的通知、收件人和站内投递状态是第一阶段通知事实。
- PC Web 通过生成的 HTTP 客户端和 TanStack Query 轮询通知列表与未读计数。
- 轮询间隔、窗口聚焦策略、增量游标和缓存时间在前端性能基线中确认；页面不可见时应减少无效请求。
- 第一阶段不部署 WebSocket、SSE、企微、微信、短信、邮件、JPush 或原生推送实现。
- 外部渠道只定义稳定的内部 `ChannelAdapter` 边界，不创建没有真实凭据、测试账号和交付范围的伪适配器。

选择轮询的原因是第一阶段只有 PC Web 接入站内通知，通知也不是毫秒级协作场景。TanStack Query 已在前端基线内，轮询易于鉴权、重连、监控和测试。内部移动端与外部端虽已进入客户端范围，但其通知呈现仍待独立确认。只有在接入范围、通知时效、在线连接规模或服务器压力出现证据后，才评估其他客户端通知以及 SSE/WebSocket。

### 3. 通知、任务与业务事实分离

- 业务模块决定为什么通知、何时请求通知、关联哪个资源以及允许的收件范围。
- 通知中心负责实际收件人解析、模板渲染、偏好裁决和渠道投递，不读取业务表猜测触发条件。
- 需要用户认领、完成、超时或留下处理结果的工作必须由 Workflow、领域模块或 Task Center 表达；通知只负责提醒。
- 发送一条通知不能关闭任务、推进审批、修改业务状态或证明用户已处理。
- 通知中的业务摘要是展示快照，不成为客户、订单或其他领域事实源。点击后必须从拥有模块重新读取当前数据。

业务模块通过明确 `NotificationIntent` 或等价契约请求通知，不直接调用站内表或外部渠道。由领域事件触发时，也必须有拥有模块维护的显式事件到通知意图映射，通知中心不订阅所有事件后基于名称猜测。

### 4. 站内通知是可靠投递通道

一个被接受的通知意图先在 PostgreSQL 中形成稳定通知和收件人事实，再进行各渠道投递。第一阶段站内通道根据偏好策略产生展示、延后或抑制决定，并保存决定原因；即使被抑制，通知意图和裁决记录仍可审计。

站内记录包含稳定通知 ID、通知类型、实际收件人、模板版本、渲染快照、来源、资源引用、创建时间、优先级、偏好裁决和安全深链引用；具体字段与枚举等待契约评审。

用户主动打开或调用已读接口才能改变站内已读状态。外部服务商回执、链接预取、邮件打开像素或管理员查看不能自动把站内通知标为已读。

### 5. 模板使用开源 Mustache 和自研版本控制

通知模板由 `notifications` 所有，不放入通用字典/参数中心。每个模板声明稳定模板键、Owner、通知类型、变量 JSON Schema、允许渠道、内容和不可变发布版本。

使用开源 Mustache 进行受限、无逻辑变量替换，项目自研模板注册、发布、版本、变量校验、渠道格式和错误映射。选择 Mustache 的原因是语法小、无业务脚本和易于跨渠道审查；具体 Node 包版本在实现时锁定。

第一阶段站内模板只输出纯文本标题、纯文本正文和结构化安全深链，不开放任意 HTML。禁用未注册 Helper、三花括号原始输出、原型链访问、文件包含、远程模板和运行时代码。变量缺失、类型不符、未知变量或渲染超限时失败，不静默发出半成品通知。

业务模块拥有具体模板的语义和变量定义；通知中心保存发布制品。通知生成后保存实际模板版本和渲染结果，后续模板更新不改变历史通知内容。

### 6. 收件人解析和快照

- 通知契约使用稳定主体、人员、Assignment 或经批准的收件范围引用，不使用显示姓名、手机号或邮箱充当身份。
- 直接收件人和范围收件人都经组织/授权公开接口解析，通知模块不查询组织表。
- 生成时保存实际收件人及解析依据、组织/Assignment 版本或必要快照，之后组织变化不静默改写已生成通知。
- 收件人解析为空、存在歧义或超过安全上限时按请求策略失败或进入人工可见状态，不能默认广播。
- 同一自然人因多个 Assignment 被重复解析时，是否合并由通知类型和收件契约明确，不能全局猜测。

### 7. 用户偏好和强制通知

- 偏好以稳定收件主体为基础，按通知类别和渠道表达允许、抑制、延后及免打扰窗口。
- 偏好不能授予业务访问权限，也不能修改通知的来源事实或 Task 状态。
- 账号安全、合规或其他强制类别可以声明不可完全关闭，但必须由受评审的通知类型定义，而不是渠道代码硬编码。
- 免打扰影响非紧急渠道投递时间，不改变通知产生时间；延迟消息只是唤醒机制，PostgreSQL 中的投递计划和偏好裁决才是事实。
- 每次投递保存使用的偏好版本、裁决结果和原因，便于解释“为什么发/没发/何时发”。

第一阶段可只提供最小偏好契约与站内注意力行为；没有外部渠道时不伪造短信、邮件或企微偏好数据。

### 8. 深链使用应用注册表，不存任意 URL

通知保存 `application_id/route_id`、稳定资源引用和允许的非敏感路由参数。路由必须由 `app-registry` 注册并声明所需权限，不能保存任意外部 URL、凭据、Token 或完整敏感查询参数。

用户点击通知时，PC Web 通过应用注册表解析路由，目标页面和 API 重新执行当前授权。收到通知不等于获得资源访问权；权限已撤销或资源已删除时显示稳定的无权/不存在状态，不泄露历史敏感摘要。

### 9. 幂等、调度和外部渠道交付

- 通知意图必须携带由生产者作用域限定的幂等键。重复请求返回同一通知结果，不重复创建收件记录。
- 批量收件按稳定通知 ID 与收件人 ID 去重，不能使用渲染文本去重。
- 延迟通知的权威计划保存在 PostgreSQL；RabbitMQ 延迟消息只负责到点唤醒，执行时重新检查取消、偏好和当前策略。
- 每个渠道拥有独立投递尝试、超时、限流、退避、死信和人工重放策略。
- 外部服务商的“已受理”“已送达”和用户阅读分别建模，不把 HTTP 200 记作用户已读。
- 外部投递失败不删除站内通知，也不回滚业务事务；如果某项业务必须确认触达，应建模为 Task、回执业务流程或人工升级，而不是依赖通知状态。
- 人工重放需要权限、原因和审计，并保持同一渠道幂等键，避免重复扣费或骚扰用户。

### 10. 渠道地址与认证身份分离

企微 `userid`、手机号、邮箱、设备 Token 等是通知渠道地址，不是 Keycloak 认证主体或组织成员事实。地址记录需要来源、验证状态、有效区间、用途、失败/退订状态和受控关联，但通知模块不得查询 Keycloak 数据库或复用 Keycloak 联合身份表作为投递地址表。

未来接入渠道时优先使用服务商官方 API、协议和 SDK，经 `ChannelAdapter` 隔离。领域模块和模板不接触服务商错误码、地址格式或凭据。

## 安全与隐私

- 通知请求和模板变量遵循最小化，只携带展示与路由所需数据。密码、Token、证件号、完整附件和不必要的敏感业务内容不得进入通知。
- 渠道地址属于敏感数据，需最小权限、受控展示、日志脱敏和按数据治理方案加密或令牌化。
- 模板、收件范围、强制类别、人工重放和批量发送属于高风险操作，需要服务端授权、审计和防批量误发控制。
- 列表、详情、未读数和已读写入都必须限定当前主体；不能通过通知 ID 枚举他人通知。
- 深链和模板输出不信任用户输入；第一阶段使用纯文本，后续 HTML/Markdown 必须独立引入上下文正确的清洗策略。

## 可观测性

- 指标至少覆盖意图接收、幂等命中、收件人解析失败、生成延迟、未读数、偏好抑制/延后、模板失败、队列积压、各渠道成功率/延迟/重试/死信和轮询请求量。
- 日志和追踪使用通知 ID、意图 ID、模板版本、收件人内部引用、投递 ID、幂等键摘要和 Trace ID，不记录完整正文、渠道地址或凭据。
- 健康检查区分 PostgreSQL 事实源、RabbitMQ Worker、Redis 缓存及每个启用渠道；未启用渠道不应影响第一阶段就绪状态。

## 测试要求

- 契约测试覆盖通知意图、收件引用、模板变量、偏好、站内状态、游标分页和稳定错误。
- 幂等测试覆盖重复意图、重复事件、批量重复收件人、Worker 崩溃和人工重放。
- 模板安全测试覆盖缺失/多余变量、原型链访问、原始输出、恶意字符、超大输入和未知版本。
- 授权测试覆盖列表、详情、未读数、已读、深链、批量操作和跨主体枚举。
- 集成测试覆盖收件人快照、偏好抑制/延后、RabbitMQ 重试/死信、通知与 Task 分离及外部渠道失败不影响站内事实。
- PC Web 测试覆盖轮询去重、页面聚焦、未读数一致性、分页、点击后重新授权和无权/资源不存在状态。
- 第一阶段只使用业务中立通知类型，不创建历史材料中的 CRM 提醒、预警或收件角色。

## 已考虑的方案

### Novu 或完整开源通知平台

能够快速接入多渠道和可视化工作流，但会引入独立用户、模板、偏好、存储、Worker 和权限模型。第一阶段只有站内渠道，与既有平台能力重复较多，因此不采用；渠道数量和运营编排需求显著增长时可通过适配器重新评估。

### 业务模块直接发送站内或外部消息

初期代码少，但会复制模板、去重、偏好、渠道地址、重试和审计，并让服务商依赖进入领域模块，因此不采用。

### 第一阶段即使用 WebSocket/SSE

能降低可见延迟，但增加连接管理、网关、会话续期、断线补偿和容量验证。当前轮询足以满足 PC Web 通知列表，因此暂不采用。

### 自研通知控制面 + 开源 Mustache + 渠道适配器

复用既有数据库、消息和授权能力，保持业务事实与外部投递边界清晰，并能随已确认渠道逐步扩展，因此采用。

## 影响

- 项目需要维护通知意图、模板版本、收件快照、偏好、站内状态、渠道适配和运营处置能力。
- 第一阶段通知存在轮询可见延迟，但部署和故障模型更简单。
- 外部渠道延期意味着系统内已有通知，但不能主动唤醒未打开 PC Web 的用户；需要主动触达的业务必须等渠道范围确认后评估。
- 后续渠道增加时继续复用站内事实和投递记录，不改变领域模块通知契约。

## 采用外部渠道或实时连接的触发条件

- 企微、微信、短信、邮件或原生客户端被正式纳入交付范围，并明确账号/地址来源、模板审核、费用和测试环境。
- 业务证明 PC Web 轮询延迟导致实际处置问题，而不是仅追求界面即时感。
- 渠道数量、模板运营和偏好复杂度高到自研控制面维护成本超过外部平台接入成本。

## 待后续决策

- 通知意图、模板、偏好、站内状态、深链和投递的具体 HTTP/事件契约。
- 第一阶段轮询、分页、保留、归档、未读计数和注意力行为。
- 通知类别、强制策略、收件范围、批量上限和模板发布权限。
- 每个外部渠道的产品范围、地址来源、服务商、成本、合规和失败升级策略。

## 非目标

- 本 ADR 不定义任何 CRM 通知、模板、触发条件、收件人、优先级或 SLA。
- 本 ADR 不确认企微、微信、短信、邮件、JPush、WebSocket 或 SSE 进入第一阶段。
- 本 ADR 不建设公告、营销自动化、呼叫中心或通用规则引擎。
- 本 ADR 不使用通知状态替代 Task、审批、业务状态或合规送达证明。
