# ADR-0013：版本化表单与业务配置中心

- 状态：已接受
- 日期：2026-07-22
- 决策人：项目负责人
- 适用范围：`form-schema`、`business-configuration`、工作台表单渲染和 `packages/config`
- 依赖决策：ADR-0001、ADR-0003、ADR-0007、ADR-0009、ADR-0010、ADR-0011

## 已知事实

- CRM 具体表单、字典项、参数键、作用范围和业务规则尚未确认。
- PC Web 使用 React 19、Ant Design 6 和 ProComponents，采用显式、可测试的前端结构。
- Workflow 需要引用稳定表单版本，但不拥有业务提交数据。
- 项目负责人确认使用 JSON Schema + Ajv，自研轻量表单渲染和版本化字典/参数中心，不引入完整低代码平台。

## 允许的假设

- 第一阶段只建设能够验证平台边界的通用表单、字典和参数 walking skeleton。
- 表单定义和业务配置可以在 PostgreSQL 保存不可变发布版本，并使用 Redis 缓存已解析结果。
- 发布与缓存失效事件通过 Transactional Outbox 和 RabbitMQ 可靠传播。

## 禁止的假设

- 不从历史材料创建客户来源、等级、无效原因、SLA、佣金等具体字典或参数。
- 不把任意 JavaScript、SQL、模板表达式或远程代码放入表单和业务配置执行。
- 不把核心状态机、金额算法、权限规则、审批路线或数据模型变成无类型动态配置。
- 不把前端隐藏、禁用或校验视为安全边界。
- 不在本 ADR 中定义具体参数作用范围、优先级、审批路线、缓存 TTL 或表单字段组件全集。

## 职责分离

| 关注点 | 所有者 | 事实源 |
|---|---|---|
| 环境变量、服务地址、连接参数和秘密引用 | `packages/config` | 部署配置与秘密存储 |
| 字典定义、字典项、业务参数及发布版本 | `business-configuration` | PostgreSQL |
| 通用表单定义、UI 元数据和发布版本 | `form-schema` | PostgreSQL |
| 具体业务表单语义和提交数据 | 对应领域模块 | 领域模块数据库 |
| 表单的 PC Web 渲染 | `apps/workbench-web` | 版本化表单定义 |
| 流程实例与人工任务 | `workflow`/Flowable | Flowable，经 Facade 访问 |

### 1. 表单协议采用 JSON Schema 2020-12 与开源 Ajv

表单数据结构和校验规则采用 JSON Schema 2020-12。服务端使用开源 Ajv 严格模式校验；浏览器可以使用同一 Schema 提前反馈，但服务端校验结果是最终裁决。

选择 JSON Schema 与 Ajv 的原因：协议开放、跨端、可版本化并有成熟验证器，能够把数据约束与 React 组件实现分开。项目不自研 Schema 语言或验证引擎，只自研注册、发布、渲染适配和项目错误映射。

允许的关键字、格式、最大深度、大小、引用方式和自定义扩展必须形成受控方言。默认禁用远程 `$ref`、动态代码执行和未经注册的自定义关键字，防止网络访问、拒绝服务和行为漂移。

### 2. 自研 `form-schema` 控制面

`packages/platform-modules/form-schema` 负责：

- 表单身份、Owner、草稿、不可变发布版本、内容摘要和兼容元数据。
- JSON Schema 与独立 UI Schema 的静态校验、发布和按版本读取。
- 可用组件、格式和扩展关键字注册表。
- 为 Workflow、领域模块和工作台提供稳定 `FormDefinitionReference`。

JSON Schema 只表达数据结构和校验；UI Schema 只表达布局、组件名称、显示顺序和安全展示元数据。UI Schema 不包含模块导入路径、任意 HTML、脚本、SQL、网络请求或授权判断。

具体业务表单由其领域模块拥有语义和源资产，通过正式发布接口注册。`form-schema` 保存运行时发布制品并执行通用约束，不因此拥有客户、订单或其他业务字段。

### 3. 自研轻量 Ant Design 渲染器

PC Web 首阶段在 `apps/workbench-web` 内自研轻量 Schema Renderer：

- 使用 Ant Design Form、Ant Design 6 和 ProComponents 的白名单字段注册表。
- 根据 JSON Schema 生成数据约束，根据 UI Schema 选择布局和已注册组件。
- 对未知组件、格式或 Schema 版本明确失败，不动态导入任意模块。
- 复杂业务交互仍使用代码编写的页面组件，不强行塞入通用 Schema。

渲染器在第二个实际客户端证明复用前不提前放入 `shared-ui`。如果未来提升为共享组件，仍不得让 UI 组件类型进入服务端表单契约。

不采用完整 Formily 或通用低代码平台，原因是它们会引入额外 Schema 方言、表达式运行时、组件状态和设计器模型，与 Ant Design 6、服务端 Ajv 和项目权限边界形成重复抽象。出现大量运营自助搭建需求后再独立评估设计器，而不是让第一阶段承担完整低代码平台复杂度。

### 4. 表单定义与提交数据分离

- `form-schema` 不保存用户提交的业务表单数据。
- 领域模块接收提交后，使用指定发布版本在服务端校验，再执行授权、领域不变量和数据库约束。
- JSON Schema 校验通过只代表形状有效，不代表操作有权限、业务状态允许或引用对象存在。
- 领域记录或 Workflow 实例保存准确的表单定义 ID、发布版本和内容摘要；需要长期举证时可以保存经过批准的必要展示快照。
- Flowable 变量只保存稳定表单引用、路由所需值和必要审批快照，不复制完整提交对象。
- 已启动流程和已保存业务记录继续使用其绑定版本；发布新版本不会追溯改变历史数据解释。

### 5. 自研 `business-configuration` 模块

新建 `packages/platform-modules/business-configuration`，在一个模块内管理两个相关但不同的子域：

- Dictionary：稳定字典类型、字典项代码、显示文本、排序、可用状态、扩展元数据和发布版本。
- Parameter：稳定参数键、数据类型、验证 Schema、允许作用范围、解析规则、Owner、默认策略和发布版本。

选择自研的原因是业务配置必须与项目组织授权、审计、版本、生效区间、影响预览和业务快照结合。Apollo、Nacos 等开源配置中心主要解决分布式应用技术配置与推送，不负责领域参数语义、稳定字典代码或业务事实复现，因此不作为业务配置事实源。

模块复用 PostgreSQL、Drizzle、Ajv、Redis 和 Outbox/RabbitMQ，不自研数据库、Schema 验证器、缓存或消息系统。

### 6. 字典规则

- 字典类型和字典项使用稳定机器代码；显示名称不作为数据库关联或业务判断依据。
- 已发布并被引用的代码不可原地改成另一语义，也不能物理删除；应停用旧项并发布新代码。
- 停用只阻止新的选择，历史数据仍能按当时版本解析和展示。
- 字典项排序、文本和安全扩展元数据可以版本化变化，但不能让扩展元数据承载任意可执行规则。
- 领域模块拥有字典语义并注册命名空间；其他模块不得根据显示文本推断业务含义。
- 不稳定、影响状态迁移或需要编译期穷举的核心枚举继续由领域契约和代码管理，不自动改成动态字典。

### 7. 参数规则

- 每个参数必须先注册稳定键、Owner、类型、验证 Schema、是否必需、允许作用范围和缺失时的失败策略，之后才能创建值版本。
- 参数值优先使用明确类型，不把所有内容塞入无约束 JSON。
- 作用范围和覆盖优先级由参数定义显式声明；平台不提供一个可以任意叠加组织、用户、环境的隐式全局优先级。
- 解析结果包含值、定义版本、值版本、作用范围和生效区间，调用方不能只拿到无法追溯的裸值。
- 高风险业务动作在所需参数缺失、版本不兼容或无法解析时失败关闭；展示类配置是否允许短时旧缓存由参数策略明确。
- 密码、Token、数据库连接、COS 密钥、证书私钥等秘密不得进入参数中心。
- 参数只能提供领域代码已定义的输入，不能动态新增数据库字段、权限、状态迁移、SQL 条件或任意动作。

### 8. 版本、发布与生效

- 草稿可以编辑；发布制品一旦生成即不可修改，使用单调版本和内容摘要识别。
- “发布版本”和“何时在哪个范围生效”分离。生效记录包含明确版本、范围和有效区间，避免修改一个全局当前值覆盖历史。
- 重新采用历史内容通过新的生效记录完成，不篡改历史发布或审计记录。
- 生效区间不能形成未定义的重叠；具体覆盖规则由参数或字典定义声明并测试。
- 发布和生效需要服务端授权、变更原因、差异、影响预览和审计。是否额外走 Flowable 审批由风险策略决定，本 ADR 不预设审批路线。
- 发布事务写入 Outbox；消费者幂等刷新 Redis 和本地缓存。Redis 键必须包含版本，PostgreSQL 始终是事实源。
- 业务事实若依赖配置结果，必须记录所用版本；金额、归属或其他需可复现结果还应保存必要输入或结果快照，不能只回查“当前配置”。

### 9. 技术配置保持独立

`packages/config` 负责启动时加载和类型校验环境变量、服务地址、连接池、超时以及秘密引用。它不提供业务后台编辑，不保存字典或业务参数，也不把秘密值写入 PostgreSQL、日志或前端。

技术配置使用开源验证库和项目自研薄加载约定。具体验证包随工程依赖初始化锁定；秘密存储产品与动态 Feature Flag 系统在部署和安全主题中另行确认。

## 安全与审计

- 表单定义、字典和参数的创建、评审、发布、生效、停用和恢复均需要独立权限及审计。
- 前端隐藏字段、只读组件和选项过滤不构成授权；服务端重新校验全部输入和资源权限。
- Schema 和 UI Schema 不允许任意 HTML、脚本、远程组件、远程 `$ref` 或未经批准的 URL。
- 敏感值不得通过字典、参数、默认值、帮助文本或表单 Schema 下发浏览器。
- 管理界面必须预览版本差异和影响范围，不能直接编辑当前生效发布制品。

## 失败、缓存与兼容

- Schema 不合法或包含未知关键字/组件：拒绝发布，不允许运行时猜测降级。
- 发布成功但消息未送达：Outbox 重发；消费者按发布 ID 幂等；缓存使用版本键并可通过对账刷新。
- Redis 不可用：从 PostgreSQL 读取或按定义的失败策略处理，不能让缓存成为配置事实源。
- 新表单版本不兼容旧提交：旧记录继续使用旧版本；迁移数据必须有独立方案，不能通过修改历史 Schema 解决。
- 参数版本不兼容调用方：调用方失败关闭并产生可观测错误，不自动把字符串强转为其他业务类型。
- 定时生效任务遗漏或重复：运行时按 PostgreSQL 有效区间解析，对账任务修复缓存和投影，调度消息不成为生效事实。

## 可观测性

- 指标覆盖 Schema/配置发布成功与失败、生效延迟、解析失败、缓存命中与过期、未知组件、服务端校验失败和版本使用分布。
- 日志记录定义 ID、版本、作用范围、发布/生效 ID、Owner 和 Trace ID，不记录秘密或不必要的表单提交数据。
- 健康检查区分 PostgreSQL 事实源、Redis 缓存和 RabbitMQ 传播状态；缓存或消息不可用不能伪造发布失败或成功。

## 测试要求

- 使用 JSON Schema 官方测试思路覆盖受支持方言，并验证前端提示与服务端 Ajv 裁决的一致边界。
- 契约测试覆盖未知关键字、远程 `$ref`、未知组件、超深/超大 Schema 和恶意输入。
- 版本测试覆盖草稿修改、发布不可变、定时生效、重叠拒绝、历史解析、重新激活和缓存失效。
- 字典测试覆盖代码稳定、停用后历史展示和显示文本变更不影响业务判断。
- 参数测试覆盖类型、范围、优先级、缺失失败、旧版本兼容和敏感值拒绝。
- 第一阶段只创建业务中立样例，不把历史材料中的 CRM 字段、SLA 或业务规则固化为配置。

## 已考虑的方案

### Formily 或完整低代码平台

能快速获得设计器和复杂联动，但会引入另一套 Schema、表达式和运行时状态，扩大安全、兼容和升级范围。当前没有足够的运营自助搭建需求，因此不采用。

### Apollo、Nacos 作为统一配置中心

适合技术配置推送，但不能自然表达领域 Owner、稳定字典代码、有效期版本、业务快照和表单发布。技术与业务配置混在一起还会扩大配置管理员权限，因此不采用为业务配置事实源。

### 全部硬编码

最容易测试，但字典文本和明确允许调整的参数每次都需要发版，也无法为运行时业务事实记录配置版本，因此不采用。

### JSON Schema + Ajv + 自研轻量平台层

复用开放标准和成熟验证器，同时让版本、授权、领域所有权和 Ant Design 渲染保持在项目控制范围内，因此采用。

## 影响

- 项目需要维护受控 JSON Schema 方言、UI Schema、字段注册表、发布流程和兼容测试。
- 动态能力被有意限制，复杂业务页面和规则仍需代码实现，不能承诺“零代码搭建全部 CRM”。
- 领域模块必须记录配置版本并处理缺失或不兼容，而不能随处读取无版本全局值。
- 后续建设设计器时可以复用发布模型，但必须单独评估权限、表达式沙箱、迁移和用户体验。

## 待后续决策

- 参数作用范围、优先级、缓存策略、生效调度和风险分级。
- 业务配置管理界面、发布审批策略和 Feature Flag 能力。

## 非目标

- 本 ADR 不定义任何 CRM 表单、字段、字典项、参数值、SLA 或规则。
- 本 ADR 不建设拖拽设计器、通用规则引擎、脚本沙箱或完整低代码平台。
- 本 ADR 不让表单模块保存领域提交数据或决定领域状态。
- 本 ADR 不把业务配置中心作为秘密管理、部署配置或动态数据库建模工具。
