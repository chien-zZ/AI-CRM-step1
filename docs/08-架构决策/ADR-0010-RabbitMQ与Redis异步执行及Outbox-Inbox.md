# ADR-0010：RabbitMQ 与 Redis 异步执行及 Outbox/Inbox

- 状态：已接受
- 日期：2026-07-22
- 决策人：项目负责人
- 适用范围：异步事件、后台任务、延迟触发、周期调度、重试、死信和短期协调状态
- 依赖决策：ADR-0003、ADR-0009

## 已知事实

- 第一阶段需要业务中立的异步执行底座，但具体 CRM 事件、倒计时、SLA 和调度周期尚未确认。
- HTTP API 与 Worker 已是独立组合入口，领域模块只能依赖契约和 `platform-sdk`。
- Flowable、业务状态、统一任务投影、提醒和后台 Job 已被划分为不同事实源或执行机制。
- 项目负责人确认第一阶段直接使用 RabbitMQ 和 Redis，并自研 Transactional Outbox/Inbox。

## 允许的假设

- RabbitMQ 和 Redis 以独立开源基础设施运行，通过项目适配器接入。
- 第一阶段采用至少一次投递语义，允许消息重复，不承诺全局严格顺序或端到端恰好一次。
- `apps/worker` 承载 Outbox 发布、RabbitMQ 消费、延迟触发和周期任务执行。

## 禁止的假设

- 不从历史材料推断任何具体业务倒计时、重试次数、SLA、路由键或队列名称。
- 不把 RabbitMQ、Redis 或延迟消息状态当成领域事实源。
- 不默认 RabbitMQ 与业务数据库之间存在分布式事务。
- 不在本决策中预选 RabbitMQ/Redis 版本、集群拓扑、托管方式、客户端库、延迟消息插件、ORM 或表结构。

## 决策

### 1. RabbitMQ 使用开源产品，不自研消息代理

RabbitMQ 负责可靠异步传输、路由、消费者确认、受控重试、死信隔离和一次性延迟触发。它是消息传送与执行基础设施，不是事件或业务状态的事实源。

选择开源 RabbitMQ 的原因：消息确认、持久化、流控、路由、死信和运维工具是成熟的通用能力，自研成本和数据丢失风险高，也不构成项目差异化能力。项目只自研适配器、拓扑声明、契约校验和运行策略，不修改 RabbitMQ 源码。

生产队列必须使用显式声明的交换机、队列、绑定、持久化、发布确认、手动消费确认、预取、重试和死信策略。具体拓扑进入 `contracts/asyncapi/`，不能散落在业务代码中。

### 2. Redis 使用开源产品，但职责受限

Redis 用于缓存、短期幂等加速、限流计数、租约或分布式执行协调等可重建状态。需要单实例执行的周期扫描可以使用带所有权令牌和过期时间的 Redis 锁，但任务是否应执行仍必须重新读取权威状态。

Redis 不保存唯一业务事实，不作为耐久 Inbox，不承载领域事件，不作为第一阶段的一次性延迟队列。Redis 数据丢失后，系统必须能够从数据库、RabbitMQ 或外部事实源恢复；依赖锁的高风险任务在 Redis 不可用时应暂停或失败关闭，不能无锁并发执行。

选择开源 Redis 的原因：高性能缓存和短期协调是成熟通用能力。项目自研的只是键命名、TTL、失效、降级和封装策略，不自研缓存服务器。

### 3. 自研 Transactional Outbox

产生领域事件或可靠异步请求时，业务状态变更与 Outbox 记录必须写入同一个本地数据库事务。事务提交后，Outbox Publisher 才可以将消息发布到 RabbitMQ；收到 Publisher Confirm 后再推进发布状态。

选择自研 Outbox 适配层的原因：Outbox 必须接入项目自己的事务边界、模块所有权、事件契约、迁移、审计和可观测性，通用中间件无法替项目决定这些语义。这里的“自研”是实现一个小而明确的项目组件，不是自研数据库或消息代理。

Publisher 在“RabbitMQ 已接收但数据库尚未标记完成”时崩溃会产生重复消息，因此系统只保证至少一次投递。Outbox 记录必须支持稳定消息标识、事件类型与版本、发生时间、生产者、关联/因果标识、载荷引用或载荷、发布状态、尝试信息和错误诊断；具体表结构等待数据库与 ORM 决策。

### 4. 自研 Transactional Inbox

每个有副作用的消费者必须以稳定的 `message_id/event_id + consumer` 作为去重键。Inbox 去重记录与消费者产生的本地状态变更应在同一个本地数据库事务中提交，成功后才确认 RabbitMQ 消息。

选择自研 Inbox 适配层的原因：幂等完成的定义属于具体消费者和模块事务，不能只靠 RabbitMQ 消息标识或 Redis TTL 判断。Redis 可以加速近期重复检查，但数据库中的耐久 Inbox 才是去重依据。

如果消费动作包含 Flowable、对象存储或外部 HTTP 等远程副作用，不能伪装为单事务。消费者必须先保存可恢复的执行状态，向外部系统传递幂等键，并通过重试与对账收敛。

### 5. 事件契约与执行契约分离

- `contracts/events/` 保存传输中立的 CloudEvents/JSON Schema 领域或平台事件，不出现交换机、队列、重试次数和 RabbitMQ 客户端类型。
- `contracts/asyncapi/` 保存 RabbitMQ 通道、绑定、路由和投递语义，并引用事件契约。
- `contracts/jobs/` 保存 Worker 私有任务载荷。Job 是“如何执行”，不能被其他模块当成稳定领域事件订阅。
- 领域模块只通过事件发布接口、任务调度接口或 `platform-sdk` 使用能力，不直接调用 RabbitMQ/Redis 客户端，也不能访问 Outbox/Inbox 表。

### 6. 延迟、周期任务、重试与死信

- 一次性延迟任务由 RabbitMQ 承载，到期消息只是唤醒信号；采用延迟消息插件还是 `TTL + DLX` 在部署设计时另行确认。
- 周期任务由 Worker 调度入口触发。权威计划及最后执行结果必须保存在可恢复的数据或版本化配置中，Redis 只协调多实例执行。
- 所有 Job 使用确定性幂等键，并在执行前重新检查权威状态、目标版本和是否仍满足条件。取消业务动作不能只依赖删除一条延迟消息。
- 瞬时错误采用有上限、有退避的重试；不可重试错误和耗尽重试的消息进入死信。禁止无限立即重新入队。
- 重试次数、退避、超时、并发、优先级和死信处理由每个事件或 Job 的运行策略明确，不能使用一个隐式全局值覆盖所有任务。
- 必须提供从权威状态扫描遗漏任务、重放事件和修复 Outbox/Inbox 漂移的对账入口。

### 7. 顺序、一致性与兼容性

- 不保证不同聚合或不同队列之间的全局顺序。确需同一对象有序时，事件必须携带聚合标识和单调版本，消费者拒绝状态回退并能对账。
- 事件消费者必须兼容重复、延迟、乱序和新旧版本并存。
- 已发布事件采用向后兼容演进；破坏性变更发布新事件版本，并在迁移期并行支持。
- RabbitMQ 不可用时，本地业务事务仍可提交 Outbox，发布器恢复后补发；Outbox 积压超过阈值必须告警。

## 安全与可观测性

- RabbitMQ 和 Redis 使用独立最小权限凭据、受控网络访问和加密传输；凭据只通过配置引用注入。
- 消息只携带完成处理所需的最少数据。密码、Token、完整附件和不必要的敏感信息不得进入消息或日志。
- 日志和追踪统一记录 `message_id/event_id`、事件类型与版本、生产者、消费者、`correlation_id`、`causation_id` 和 `trace_id`。
- 指标至少覆盖 Outbox 最老未发布时长与积压量、发布失败、消费延迟、重试、死信、Inbox 重复命中、处理时长、连接状态和 Redis 协调失败。
- 健康检查区分存活与就绪。RabbitMQ、Redis 或数据库不可用时，Worker 应停止领取其无法安全完成的工作。

## 测试要求

- 契约测试验证事件 Schema、AsyncAPI 引用、兼容性和 Job 载荷。
- 集成测试覆盖事务回滚不发布、提交后发布、Publisher Confirm 丢失、重复投递、消费者崩溃、乱序、重试耗尽、死信与重放。
- 故障测试覆盖 RabbitMQ、Redis 和数据库分别不可用，以及恢复后的积压排空和对账。
- 幂等测试必须证明同一消息重复处理不会产生重复业务副作用。
- 第一阶段仅使用业务中立 walking skeleton 事件和任务，不编码历史材料中的 CRM 倒计时或状态规则。

## 已考虑的方案

### BullMQ + Redis

组件较少且适合纯 Node.js 队列，但会让 Redis 同时承担缓存、协调、任务队列和延迟队列。项目负责人选择直接建设 RabbitMQ 消息基础设施，以获得更明确的路由、消费者确认和死信边界，因此不采用 BullMQ。

### 只轮询数据库 Outbox，不使用消息代理

事务边界最简单，但跨消费者路由、背压、死信隔离和独立扩缩容能力有限。它可作为 RabbitMQ 故障期间的事实保留方式，不能替代正式传输层。

### 直接发布 RabbitMQ，不使用 Outbox/Inbox

会出现业务提交成功但消息丢失，或消息成功但业务回滚的双写窗口；消费者重试也可能产生重复副作用，因此不采用。

### RabbitMQ + Redis + 自研 Outbox/Inbox

复用成熟基础设施，同时把事务一致性、模块语义和幂等收敛保留在项目控制范围内，因此采用。

## 影响

- 第一阶段就需要部署、监控、备份配置和演练 RabbitMQ 与 Redis，运维复杂度高于单 Redis 方案。
- 项目需要维护 RabbitMQ/Redis 适配器、Outbox Publisher、Inbox 消费包装、对账工具和死信处置流程。
- RabbitMQ 与数据库之间仍是最终一致，调用方必须接受短暂延迟并设计可见的处理中或失败状态。
- 后续拆分服务时可以保留事件契约和 Outbox/Inbox 语义，只替换适配与部署拓扑。

## 后续决策

- 数据库、ORM、迁移和应用数据库内的 Outbox/Inbox 所有权已由 ADR-0011 确认。
- RabbitMQ 与 Redis 的版本、客户端库、部署拓扑、高可用、备份和容量基线。
- 一次性延迟采用 RabbitMQ 插件还是 `TTL + DLX`。
- 通用调度入口、运行策略 Schema、死信管理和人工重放授权契约。

## 非目标

- 本 ADR 不定义任何 CRM 事件、队列、倒计时、SLA、提醒或周期。
- 本 ADR 不承诺跨数据库、RabbitMQ、Flowable 和外部服务的分布式事务或恰好一次处理。
- 本 ADR 不把所有模块调用异步化，也不使用 RabbitMQ 实现同步 RPC。
- 本 ADR 不授权业务代码直接使用 RabbitMQ 或 Redis。
