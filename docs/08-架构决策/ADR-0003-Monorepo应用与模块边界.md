# ADR-0003：Monorepo 应用与模块边界

- 状态：已接受
- 日期：2026-07-22
- 决策人：项目负责人
- 适用范围：整个 monorepo

## 背景

历史方案把后端集中在 `apps/server`，并通过 `packages/shared-core` 共享 API 客户端、状态、校验、权限和业务辅助逻辑。随着 CRM 扩展为公司工作台，这种结构容易让运行入口、平台能力、领域逻辑和跨端共享代码逐渐混在一起。

当前项目需要支持多个 AI 任务并行开发、公共平台能力先行、业务边界逐步确认，以及未来按运行负载独立扩展 HTTP 和后台任务。仓库结构必须让依赖方向显式、可检查，并阻止未确认业务进入公共底座。

## 决策

### 可运行应用

`apps/` 只包含能够独立运行和部署的程序：

- `apps/api`：NestJS HTTP API 和可选实时通信的组合入口。
- `apps/worker`：NestJS 后台任务、Outbox 投递、调度、文件处理和外部渠道适配器的组合入口。
- `apps/workbench-web`：PC 工作台应用。
- `apps/internal-mobile`：第一阶段内部移动端应用，具体端形态由 ADR-0015 的后续决策确认。
- `apps/external-portal`：第一阶段外部端应用，独立于内部客户端的身份和 API 暴露面。
- 未来新增的其他独立客户端也放在 `apps/`，但必须先有被确认的范围。

应用是 composition root，只负责配置、依赖装配、启动和进程级生命周期，不承载平台或领域规则。

### 平台与领域模块

- `packages/platform-modules/` 保存与具体业务无关的平台能力。
- `packages/domain-modules/` 只保存已经确认边界的业务领域模块。
- `packages/platform-sdk/` 向领域模块和应用提供稳定、与厂商无关的平台接口。
- `contracts/` 保存 HTTP、事件、任务、权限、错误和共享模型契约；契约先于实现变更。
- `packages/api-client/` 保存由 OpenAPI 生成的客户端及其最薄封装。
- `packages/shared-ui/` 只接收已经证明跨应用复用的 UI，不作为工作台组件的默认存放位置。

### 依赖规则

1. `apps/*` 可以装配平台模块和已确认领域模块，但不能成为业务规则所有者。
2. 领域模块只能通过公开契约和 `platform-sdk` 使用平台能力，不直接依赖 Keycloak、Flowable、RabbitMQ、Redis 或存储厂商。
3. 平台模块不能依赖领域模块。
4. 一个模块不能查询或修改另一个模块的表。
5. 模块间不能使用深层文件导入，只能通过各包公开入口交互。
6. HTTP 和领域事件契约必须先于实现修改；消息拓扑和 Worker 任务载荷属于基础设施或私有执行契约，不能冒充领域事件。具体边界见 ADR-0010。
7. 不建立新的 `shared-core` 总共享包。共享代码必须进入职责明确的 SDK、客户端、契约、UI 或工程配置包。

## 原因

### 适合 AI 并行开发

每个任务可以被限制在明确的应用、平台模块、领域模块或契约目录中。依赖方向能够由 lint、类型检查和仓库检查自动验证，减少不同 AI 在同一共享目录中生成互相冲突的抽象。

### API 与 Worker 的运行特征不同

HTTP 请求关注低延迟、并发连接、超时和同步错误响应；Worker 关注重试、幂等、锁、长任务、死信和吞吐。分开运行可以独立扩缩容、部署和恢复，也能避免后台任务阻塞 API 进程。

### 保留模块化单体的交付效率

模块独立不等于微服务。第一阶段平台模块和领域模块可以被 `apps/api` 与 `apps/worker` 装配，并共享同一套部署基础设施。只有当负载、团队所有权或故障隔离需求得到证据支持时，才考虑拆为远程服务。

### 避免总共享包失控

`shared-core` 容易同时容纳 API 类型、状态管理、权限、校验和业务辅助函数，最终变成所有模块都能依赖的隐性耦合中心。按职责拆分后，每项共享内容都有所有者、公开接口和替换边界。

### 支持从 CRM 演进为工作台

工作台可以通过应用注册、平台 SDK 和契约接入后续业务应用，而不需要把所有业务逻辑塞进 Web 应用或单一后端目录。新业务模块可以独立确认、实现和测试，同时复用稳定的平台能力。

## 已考虑的方案

### `apps/server` 与 `packages/shared-core`

初期目录较少，但容易混合 HTTP、后台任务、领域实现和跨端共享逻辑，边界主要依赖人工约定，不利于长期扩展和 AI 并行开发，因此不采用。

### 从第一天拆分微服务

可以获得更强的运行隔离，但会过早引入网络契约、分布式事务、服务发现和部署复杂度。当前没有足够的负载或团队边界证据，因此不采用。

## 影响

- 初期 package 数量较多，需要维护公开入口、依赖规则和契约检查。
- API 与 Worker 需要各自的健康检查、日志、指标、部署和失败策略。
- 共享数据库可以作为早期部署选择，但数据所有权仍按模块划分，禁止跨模块直接访问表。
- 将模块拆为独立服务时，应保持现有 SDK 和契约边界，减少调用方式变化对领域代码的影响。
- 新增应用、平台模块或领域模块必须说明所有者、职责、非职责、公开接口和依赖方向。

## 非目标

- 本 ADR 不确认任何 CRM 领域模块。
- 本 ADR 不决定数据库、ORM、消息代理或部署拓扑。
- 本 ADR 不要求当前平台模块分别部署为独立服务。
