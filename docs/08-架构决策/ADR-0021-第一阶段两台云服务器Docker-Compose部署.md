# ADR-0021：第一阶段两台云服务器 Docker Compose 部署

- 状态：已接受
- 日期：2026-07-23
- 决策人：项目负责人
- 适用范围：第一阶段开发、测试、预发布和生产部署，`deploy/`，运行组件的部署责任
- 依赖决策：ADR-0002、ADR-0003、ADR-0004、ADR-0009、ADR-0010、ADR-0011、ADR-0012、ADR-0020

## 已知事实

- 项目负责人确认沿用历史材料中的原部署方向：两台云服务器、Docker Compose、自托管运行组件，不采用生产托管数据库、缓存或消息队列。
- 当前正式技术基线已经包含 Node 24、PostgreSQL、Redis、RabbitMQ、Keycloak、Flowable、Nginx、ClamAV，以及独立 API、Worker 和三个客户端制品。
- 腾讯云 COS 已作为生产对象存储；业务文件不会保存在应用服务器本地磁盘。
- 当前尚未确认实际并发量、数据量、云地域、机器规格、网络带宽、RPO、RTO、备份保留期和值班能力。
- Docker Compose 只编排单台主机。两台服务器需要各自部署 Compose Project，不能被描述为一个跨主机 Compose 集群。

## 允许的假设

- 第一阶段优先控制成本和运维组件数量，可以接受基础设施故障后的人工恢复窗口。
- API 可以在两台服务器分别运行一个或多个副本；会话和业务事实不保存在单个 API 进程内存中。
- PostgreSQL 全量备份、WAL、配置备份和恢复材料可以写入与服务器故障域分离的受限 COS Bucket。

## 禁止的假设

- 不把“两台服务器 + 两个 API 副本”表述为数据库、消息、认证或入口的真正高可用。
- 不在两台服务器上伪造需要三节点仲裁的 Redis Sentinel 或 RabbitMQ Quorum 高可用集群。
- 不因为沿用历史部署形态而恢复历史 Node 22、Prisma、自建 JWT、BullMQ、HeroUI 或巨型集成网关方案。
- 不默认每日全量备份等于已满足任何 RPO/RTO；WAL 是否连续可恢复必须通过演练证明。
- 不在仓库、Compose 文件、镜像、日志或前端制品中保存生产 Secret。

## 决策

### 1. 生产采用两台腾讯云 Ubuntu CVM 与 Docker Compose

- 生产购买两台位于同一地域、使用私有网络互通的腾讯云 Ubuntu CVM。
- 每台服务器运行独立、版本化的 Docker Compose Project；不使用 Docker Swarm 或 Kubernetes。
- API 至少部署两个副本，并分布在两台服务器上。Nginx 提供 TLS 终止后的反向代理、同站点 BFF 路由和静态制品入口。
- Worker、Keycloak、Flowable、PostgreSQL、Redis、RabbitMQ 和 ClamAV 以自托管容器运行。具体放置、端口、资源配额和副本数在实施前通过容量与故障域评审确定。
- PostgreSQL、Redis、RabbitMQ、Keycloak 和 Flowable 不暴露公网端口，只允许所需容器和受控运维来源通过私网访问。
- PC Web、内部 H5 和外部 H5 是独立构建制品，可由 Nginx 提供静态内容；微信小程序保持独立发布。

这项决策只固定部署形态，不在缺少规格和容量数据时虚构精确 CPU、内存、磁盘、连接池或队列参数。

### 2. 自研、开源与托管边界

| 能力 | 选择 | 原因 |
|---|---|---|
| CRM API、Worker、三个客户端和部署胶水 | 项目自研 | 承载项目契约、模块组合和发布规则 |
| 容器运行与单机编排 | Docker Engine + Docker Compose 开源/社区能力 | 两台机器规模下结构显式、AI 易于生成和验证，运维成本低于 Kubernetes |
| 入口代理 | 自托管开源 Nginx | 满足静态资源、TLS 后路由、BFF 同站点和 API 反向代理需求；第一阶段不部署 APISIX |
| PostgreSQL、Redis、RabbitMQ | 自托管开源版本 | 项目负责人选择原方案并接受自行承担升级、备份和恢复 |
| Keycloak、Flowable、ClamAV | 自托管开源版本 | 使用成熟产品能力，经 Adapter/Facade 隔离，不修改其源码 |
| 云主机、网络、磁盘和 COS | 腾讯云托管基础设施 | 不自建物理机、网络或对象存储；COS 同时提供业务文件与受限异地备份介质 |
| Kubernetes、Docker Swarm | 第一阶段不采用 | 当前只有两台主机，编排复杂度和仲裁要求超过第一阶段收益 |

开源意味着许可证允许使用和自行部署，不意味着没有运维成本。每个运行组件仍需要固定版本、资源限制、健康检查、升级说明、备份责任和安全公告响应。

### 3. 明确接受非高可用限制

- 如果承担 Nginx 公网入口的服务器不可用，在入口恢复或人工切换前系统不可访问。
- 单实例 PostgreSQL、Redis、RabbitMQ、Keycloak 或 Flowable 不可用时，对应能力中断。
- 两台服务器不能安全提供所有状态组件的自动仲裁；第一阶段不承诺自动故障转移和零数据丢失。
- API 双副本主要提供滚动发布和应用进程级冗余，不能抵消共享状态组件故障。
- 服务器、磁盘或地域级故障后的恢复依赖异地备份、版本化配置、镜像仓库和已演练的恢复手册。

任何对外 SLA、RPO 或 RTO 承诺都必须在容量测试和恢复演练后单独批准。

### 4. 环境与隔离

- 本地开发使用 `compose.dev.yml` 或等价分片，允许本地文件存储 Adapter 和开发专用初始化数据。
- CI/自动测试使用隔离的临时 Compose 环境，不连接共享生产数据或生产供应商账号。
- 预发布和生产使用不同数据库、Redis、RabbitMQ、Keycloak Realm/Client、Flowable 配置、COS Bucket、域名、证书和 Secret。
- 预发布尽量保持与生产相同的镜像、组件大版本和网络拓扑；资源规格可以较小。
- 环境不能由请求域名、数据库内容或运行时猜测隐式决定，必须由经过校验的部署配置明确选择。

是否为预发布单独购买长期服务器，或在两台生产服务器之外使用临时环境，等待成本和发布频率确认；预发布不得与生产共享状态数据。

### 5. 镜像、发布与回滚

- 所有应用镜像由固定 Node 24 基础镜像构建，使用不可变版本号和镜像摘要发布，不使用漂移的 `latest` 作为生产依据。
- 第三方镜像固定明确版本或摘要，并记录许可证、升级和兼容矩阵。
- 生产发布必须手动批准，按服务器逐台更新 API 副本，并在每步通过健康、就绪和关键路径冒烟检查。
- Worker 发布必须考虑旧/新 Job 契约共存、消费者停止接收、在途任务和幂等处理。
- 数据库迁移遵守 ADR-0011：先兼容扩展、再切换代码、最后清理；不得把应用镜像回滚当成数据库自动回滚。
- 回滚使用上一不可变应用镜像；不可逆数据变更必须提供前滚修复和恢复点。

### 6. 备份与恢复

- PostgreSQL 至少执行每日全量/基础备份并连续归档 WAL；备份写入受限、加密、与两台服务器分离的 COS Bucket。
- Keycloak、Flowable 和应用数据库分别备份，不假定只恢复应用数据库即可恢复完整系统。
- Redis 不是业务唯一事实源；是否启用 RDB/AOF 取决于会话恢复和缓存冷启动评审。
- RabbitMQ 是传输层；关键未完成承诺以 Outbox/Inbox 和业务状态恢复，仍需备份拓扑定义、权限、策略和必要的持久化数据。
- Compose、Nginx、Keycloak Realm、Flowable 配置和基础设施清单必须配置即代码；生产 Secret 只保存引用或加密备份。
- 上线前必须完成一次从空服务器恢复的演练，随后按批准频率复演；只验证“备份任务成功”不算恢复验证。

具体保留期、RPO、RTO、恢复顺序和责任人等待业务影响分析后批准。

### 7. 健康、安全和可观测最低要求

- 每个容器定义健康检查、启动顺序、资源限制、日志轮转和优雅停止。
- API 区分存活与就绪；依赖暂时不可用时不得继续接收无法正确处理的高风险写请求。
- 所有公网访问经 Nginx，管理端口和数据库端口不开放公网；主机使用最小安全组、受控 SSH 来源和非密码式管理认证。
- 容器不使用特权模式，不挂载 Docker Socket，不以不必要的 root 权限运行。
- 日志、指标和 Trace 必须能区分环境、服务、版本和实例，但具体观测产品另立决策。
- 备份失败、磁盘容量、证书到期、容器反复重启、数据库不可用、RabbitMQ 积压和关键健康检查失败必须可告警。

## 已考虑的方案

### 腾讯云托管 PostgreSQL、Redis 和 RabbitMQ

能够显著降低高可用、补丁和备份压力，但增加持续成本与云产品兼容验证；项目负责人选择沿用原自托管方案，因此不采用。

### Kubernetes

提供跨主机调度和扩缩容，但两节点不足以构成稳健控制面，且当前模块化单体规模不需要其复杂度，因此第一阶段不采用。

### 单台服务器运行全部组件

成本最低，但无法在发布和应用进程故障时保留第二 API 副本，也使所有状态和入口共享单一故障域，因此不采用。

### 两台服务器 Docker Compose

符合当前成本与团队阶段，结构显式且易于本地复现，但接受共享状态组件单点故障和人工恢复，因此采用。

## 影响

- `deploy/compose/` 将维护本地、测试、预发布和生产 Compose 定义或清晰分片，不创建跨主机 Compose 幻觉。
- 团队需要自行承担 PostgreSQL、Redis、RabbitMQ、Keycloak、Flowable、Nginx 和 ClamAV 的补丁、升级、容量、备份和恢复。
- 生产上线前必须补齐两台主机的服务放置、网络、规格、磁盘、域名、证书、备份、恢复和发布 Runbook。
- 当可用性、数据量或运维负担超过触发条件时，可迁移到云托管状态组件或三节点以上编排平台；模块 Adapter 和契约边界保持不变。

## 升级触发条件

满足任一条件时重新评审部署方案：

- 业务要求自动故障转移、明确 SLA，或当前人工恢复无法满足批准的 RTO/RPO。
- 单机 PostgreSQL、Redis、RabbitMQ、Keycloak 或 Flowable 故障已经成为不可接受风险。
- 发布频率、服务数量或资源隔离需求使逐台 Compose 部署持续出错。
- 需要跨可用区容灾、自动扩缩容、滚动编排或三节点仲裁。
- 补丁、备份、恢复和值班成本接近或超过托管服务成本。

## 待后续确认

- 两台 CVM 的地域、可用区、规格、磁盘和实际服务放置。
- 公网入口、DNS、TLS 证书和故障时人工切换方案。
- PostgreSQL、Redis、RabbitMQ、Keycloak、Flowable、Nginx 和 ClamAV 的固定版本。
- RPO、RTO、备份保留期、恢复责任人和演练频率。
- 预发布环境的长期资源与成本。
- Secret 管理、主机加固、漏洞扫描和具体可观测产品。

## 非目标

- 本 ADR 不承诺高可用、跨可用区容灾、零停机或零数据丢失。
- 本 ADR 不生成包含占位 Secret、未固定镜像或未评审端口的生产 Compose 文件。
- 本 ADR 不确定业务容量、客户端 SLA 或 CRM 上线日期。
- 本 ADR 不恢复历史材料中与已接受 ADR 冲突的技术方案。
