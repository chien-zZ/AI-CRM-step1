# ADR-0007：自研轻量业务授权核心

- 状态：已接受
- 日期：2026-07-22
- 决策人：项目负责人
- 适用范围：`packages/platform-modules/authorization`、`platform-sdk` 与权限契约
- 依赖决策：ADR-0003、ADR-0004

## 背景

Keycloak 已确认为统一认证中心，但认证只能回答“调用者是谁”，不能完整回答“调用者能做什么、能查看哪些业务数据”。历史材料提出了功能权限、数据范围和岗位授权，但其中具体角色、范围枚举和业务资源尚未经过当前业务调研确认。

Casbin、OpenFGA、OPA 和 Cerbos 等开源引擎各自擅长布尔权限、关系授权或策略即代码，但本项目还需要把组织、有效期任职、领域数据所有权、列表过滤和敏感字段审计组合起来。过早选定引擎会先固化未确认的授权模型，并额外引入策略语言、同步或运行服务。

## 决策

1. 第一阶段自研轻量、传输无关的业务授权核心，不引入独立的 Casbin、OpenFGA、OPA 或 Cerbos 运行时。
2. `authorization` 对外提供稳定的授权接口，至少覆盖单项检查、批量检查和数据范围解析：

   ```text
   check(principal, resource, action, context)
   batchCheck(principal, requests)
   resolveDataScope(principal, resource, action, context)
   ```

3. 权限码采用稳定、带命名空间的“资源 + 动作”语义。具体资源和动作必须由对应平台或领域模块通过权限契约声明，不能由页面临时发明。
4. 角色是可管理的权限集合，不等同于部门岗位名称。代码不得使用 `if role === ...` 代替授权检查。
5. 功能权限与数据范围分别建模和裁决。允许执行某个动作不自动意味着可以访问该资源的全部实例。
6. 数据范围解析返回版本化、类型化的结构化约束，不返回任意 SQL、ORM 查询片段或业务表名。
7. 拥有数据的模块负责把结构化范围转换为自己的查询条件。模块不能表达某项约束时必须失败关闭，不能静默忽略。
8. 对单个对象执行操作时，领域模块仍需结合资源事实执行对象级检查；列表过滤不能替代关键写操作授权。
9. 敏感字段查看、数据导出、权限管理和其他高风险动作使用独立权限，并按安全规则记录授权决策与业务审计。
10. 默认拒绝。缺失主体、权限声明、资源上下文、策略版本或无法解析的范围均不得放行。
11. Keycloak Claim 可以作为主体输入，但不能直接成为业务授权结论。业务授权不写回 Keycloak 角色作为事实源。
12. 授权实现通过内部适配接口与存储和未来策略引擎隔离。领域模块只依赖 `platform-sdk` 和权限契约。
13. 外部访问后来由 ADR-0019 区分匿名、邀请能力和 Keycloak 登录上下文。邀请凭据只证明受限能力，不得伪装为认证主体或与登录权限取并集。

## 授权职责边界

| 能力 | 所有者 |
|---|---|
| 登录身份与 Token | Keycloak |
| 内部主体上下文 | `auth-context` |
| 人员、组织、岗位、有效期任职 | `organization` |
| 权限声明、角色权限集合、授权决策 | `authorization` |
| 业务对象事实与查询转换 | 拥有该数据的平台或领域模块 |
| 高风险操作留痕 | `audit` |

授权模块不能查询领域模块的表，也不能为所有领域生成一个跨表查询。领域模块不得绕过授权接口自行解释角色名称。

## 决策结果与失败行为

- 授权结果至少能够表达允许或拒绝、稳定原因代码、策略版本和可关联的决策标识；不得把内部策略细节直接暴露给终端用户。
- 批量检查必须保持单项检查语义一致，不能因批量优化扩大权限。
- 策略或授权关系更新需要版本化并定义缓存失效；具体缓存产品和 TTL 另行确认。
- 授权依赖不可用、策略数据损坏或上下文不足时失败关闭，并产生可观测错误。
- 拒绝访问返回稳定的权限错误契约，不返回资源是否存在等可被利用的额外信息。
- 权限管理变更必须审计；普通低风险读取是否记录逐次决策，由数据安全分级决定，避免无边界日志膨胀。

## 为什么第一阶段自研

### 保持模型显式

授权接口、权限声明和数据范围类型都存在于 TypeScript 与正式契约中，AI 可以通过类型检查、契约测试和固定用例验证，不依赖隐藏的策略文本或外部关系数据。

### 数据过滤必须由数据所有者完成

通用引擎通常擅长回答单个对象是否允许，但企业工作台大量使用分页列表、统计和导出。数据范围最终必须安全地进入模块自己的查询层，这部分无法由通用布尔引擎自动替代。

### 避免过早同步复杂度

关系型授权服务需要同步人员、组织、任职和资源关系；策略服务需要持续提供上下文数据。当前模型未确认时引入同步链路只会增加双写和一致性风险。

## 已考虑的开源方案

### Casbin

适合嵌入式 RBAC/ABAC 和域模型，但有效期任职、列表数据范围、授权审计及模块查询转换仍需项目实现。当前收益不足以抵消模型字符串和适配复杂度。

### OpenFGA

适合共享、委托和复杂资源关系图。当前会额外引入关系元组同步、模型版本和服务可用性问题，且列表过滤仍需设计，因此暂不采用。

### OPA 或 Cerbos

适合策略即代码和复杂条件，但需要维护额外策略语言、策略发布以及上下文数据输入。当前权限模型尚未复杂到需要独立决策服务，因此暂不采用。

## 引入策略引擎的触发条件

出现以下情况时重新评估，并通过新 ADR 选择实现：

- 跨组织共享、委托、代理或资源关系形成稳定复杂图。
- 授权策略数量和条件复杂度超出当前类型化模型的可维护范围。
- 多个独立服务需要共享低延迟授权决策。
- 监管或组织要求策略即代码、独立策略发布和集中决策审计。
- 经过基准测试证明外部引擎能改善正确性或维护成本，并有清晰的数据同步方案。

## 影响

- 项目需要自行实现并测试授权契约、角色权限集合、决策流程和结构化数据范围。
- 自研范围必须保持有限；不得演变为通用表达式语言或另一套身份系统。
- 每个模块需要声明权限，并对数据范围到本地查询的转换负责。
- 后续替换底层策略引擎时，对领域模块暴露的 `platform-sdk` 接口保持稳定。

## 非目标

- 本 ADR 不定义任何具体业务角色、权限码或数据范围枚举。
- 本 ADR 不确认组织、人员、岗位和任职的数据结构。
- 本 ADR 不决定权限数据存储、缓存产品、管理页面或审批流程。
- 本 ADR 不允许用前端按钮隐藏代替服务端授权。
