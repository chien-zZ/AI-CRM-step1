# ADR-0018：内部人员主体关联与失效

- 状态：已接受
- 日期：2026-07-22
- 决策人：项目负责人
- 适用范围：Keycloak 内部人员、企微联合身份、`organization`、`auth-context`、`authorization` 与 BFF 会话
- 依赖决策：ADR-0004、ADR-0006、ADR-0007、ADR-0008、ADR-0017

## 已知事实

- Keycloak 是唯一认证中心，企微只能作为联合身份和快捷登录入口。
- 组织模块区分 Authentication Subject、Workforce Person、Employment 和 Assignment，并保留有效期历史。
- 内部 H5 使用 BFF HttpOnly Cookie；企微提供商登录尚未实施。
- 历史方案中的 CRM 账号密码、`account_oauth_binding` 和 `bind_ticket` 已被 ADR-0004、ADR-0006 废弃。
- 实际人员字段、组织结构、入离职流程、审批路线和失效时效目标尚未确认。

## 允许的假设

- 一名内部自然人可以先存在 Workforce Person 和 Employment，之后再获得登录主体。
- 普通浏览器保留 Keycloak 标准登录，可用于首次关联前登录、重新认证和企微入口不可用时的回退。
- 第一阶段可以由受控管理员或确定性的目录同步建立最小主体关联，不依赖完整 HRM。

## 禁止的假设

- 不使用姓名、手机号、邮箱、部门文本或其他模糊属性自动匹配人员和登录主体。
- 不信任前端提交的企微 `userid`，也不把企微通讯录记录直接视为已认证主体。
- 不因 Keycloak 登录成功或企微身份验证成功而自动创建 Workforce Person、Employment、Assignment、角色或数据权限。
- 不把关闭 Assignment 等同于离职，也不因单个 Assignment 结束而删除人员或禁用整个认证主体。
- 不从历史材料推断员工编号、人员状态、离职审批或具体权限。

## 决策

### 1. 三层身份关系分别归属

```text
企微 provider + tenant + userid
              ↓ Keycloak 联合身份
       Keycloak issuer + sub
              ↓ organization 受控有效关联
        Workforce Person
              ↓
     Employment / Assignment
```

- 企微身份与 Keycloak 用户的联合关系由 Keycloak 管理。
- Keycloak `issuer + sub` 与 Workforce Person 的有效关联由 `organization` 管理。
- Employment 和 Assignment 继续由 `organization` 管理，不能写入 Keycloak Group/Role 作为事实源。
- `auth-context` 只通过公开组织能力解析主体上下文，不读取组织或 Keycloak 数据库。
- 业务授权由 `authorization` 裁决，任何关联本身都不授予业务权限。

### 2. 主体与内部人员执行有效期和唯一性约束

- 一个有效 Keycloak `issuer + sub` 最多关联一个 Workforce Person。
- 一个 Workforce Person 默认最多关联一个有效的交互式 Keycloak 主体。
- 主体迁移或账号重建采用“关闭旧关联、创建新关联”，保留历史，不覆盖 `sub`。
- Workforce Person 可以暂时没有有效认证主体；这不删除其 Employment、Assignment 或历史责任。
- 重复关联或并发冲突必须失败关闭，不能以后写覆盖先写。

具体表名、字段、时间区间表示和迁移策略在契约与数据设计任务中确认。

### 3. 首次关联只允许两条受控路径

#### 管理员或受控预配

授权管理员或经过批准的目录预配流程，可以在拥有确定、可验证的人员映射时建立 Keycloak 主体与 Workforce Person 的关联。没有权威映射或发生冲突时进入人工处理，不执行模糊匹配。

#### 已登录员工自助绑定企微

员工先使用已关联到 Workforce Person 的现有 Keycloak 账号完成登录和近期重新认证，再在同一受控会话中发起企微 OAuth。服务端验证企微结果后，由 Keycloak 建立联合身份关系。

该路径只给既有 Keycloak 用户增加企微快捷入口，不创建新的 Workforce Person、Employment 或主体到人员关联。

仅验证了企微身份、但无法解析为已关联内部人员时，不创建正常工作台会话，也不授予组织上下文。

### 4. 企微登录身份与通讯录同步身份保持分离

同一个企微 `userid` 可能同时用于登录和通讯录同步，但二者用途和所有者不同：

- Keycloak 联合身份关系服务认证。
- 组织同步适配器可以维护受控的 `source system + tenant + source object id` 来源映射，只服务同步、冲突和回放。
- 两个边界不共享数据库表，不直接查询对方存储，也不能用通讯录映射绕过 Keycloak 建立登录主体。
- 通知投递地址同样通过正式接口维护，不能读取 Keycloak 或组织同步表形成隐式集成。

### 5. 解绑只移除企微快捷入口

- 员工自助解绑前必须完成近期 Keycloak 重新认证。
- 授权管理员可以代解绑，但必须提供原因并记录操作者；是否增加审批由后续管理规则决定。
- 解绑从 Keycloak 移除或停用企微联合身份，并撤销受影响会话。
- 解绑不删除 Keycloak 用户、主体到 Workforce Person 的关联、人员档案、Employment、Assignment 或历史审计。
- 重复解绑返回稳定幂等结果；解绑和并发登录冲突时以失败关闭和会话撤销为准。

### 6. Employment 与 Assignment 采用不同失效语义

- Employment 失效后，内部工作台访问在服务端请求边界失败关闭，即使 Keycloak 或 BFF 会话尚未自然过期也不能继续访问。
- Employment 关闭事务通过 Transactional Outbox 发布业务中立变更事件，驱动 BFF 会话撤销、授权缓存失效和相关投影更新。
- 异步撤销是加速手段，不是唯一安全边界；每次构造内部主体/授权上下文仍需拒绝无有效 Employment 的人员。
- 仅某个 Assignment 失效时，只撤销相应组织上下文和依赖它的授权，不自动禁用整个 Keycloak 用户。
- 人员有多个有效 Assignment 时，结束其中一个不能影响其他仍有效上下文。
- 是否在全部 Employment 失效后禁用 Keycloak 用户属于公司级账号生命周期策略，另行确认。

### 7. 企微通讯录变化不能删除组织历史

- 通讯录删除、停用或字段变化只形成经过适配器验证的同步输入。
- 外部记录消失不能物理删除 Workforce Person、Employment、Assignment 或历史主体关联。
- 在字段所有权和人员生命周期规则确认前，删除信号进入冲突/待处理状态，不自动推断离职。
- 同步使用来源版本和幂等键；乱序、重复和冲突不能以最后写入无条件覆盖。

## 开源与自研边界

| 能力 | 选择 | 原因 |
|---|---|---|
| 登录、重新认证、企微联合身份 | 开源 Keycloak + 自研薄 SPI/适配器 | 认证生命周期交给成熟 IdP，非标准企微协议保持可审计适配 |
| 主体与 Workforce Person 有效关联 | 自研 `organization` | 需要有效期、历史责任和组织语义，Keycloak 模型不足 |
| 企微通讯录接入 | 企微官方 API + 自研薄同步适配器 | 外部系统只是数据来源，内部模型和冲突策略必须受控 |
| 会话撤销与短期协调 | 开源 Redis + 自研会话编排 | Redis 适合短期状态，失效规则属于项目边界 |

不引入完整 HRM，不修改 Keycloak 源码，也不恢复 CRM 自建密码、绑定表或认证 Token。

## 事务、幂等与失败行为

- 组织内部的主体关联变更、审计请求和 Outbox 记录在同一数据库事务中提交。
- Keycloak 与组织数据库之间不做分布式事务；跨系统操作使用明确步骤、幂等键、状态核对和可重试补偿。
- 任一步失败都不能留下可访问但无法追溯的部分关联；不确定状态保持无权访问并进入对账。
- 管理员预配、自助绑定、解绑、Employment 关闭和同步输入必须支持幂等重试。
- 关联冲突、重新认证失败、Keycloak/Redis/企微不可用和组织上下文缺失均失败关闭。

## 授权与审计

- 建立/关闭主体关联、员工自助绑定/解绑、管理员代解绑、同步冲突和 Employment 失效都记录操作者、目标、来源、原因、结果、时间与 Trace ID。
- 审计日志只记录必要的主体引用和脱敏/摘要后的提供商标识，不记录 Token、Cookie、授权码或企微 Secret。
- 管理端操作需要独立权限并由服务端校验；前端隐藏按钮不能代替授权。
- 登录成功、存在人员关联和存在有效 Employment 是不同判断，必须分别记录失败类别。

## 可观测性与测试

- 指标覆盖主体关联成功/冲突、企微绑定/解绑、无人员关联、无有效 Employment、会话撤销延迟和同步冲突。
- Trace 串联 Keycloak 回调、主体解析、组织查询、授权和会话撤销，但不得携带认证凭据。
- 契约测试覆盖一对一有效关联、历史关闭、重复请求、并发冲突和多 Assignment。
- 集成测试覆盖已关联登录、企微已验证但人员未关联、自助绑定重新认证、管理员解绑、Employment 失效后旧会话访问拒绝。
- 对账测试覆盖 Keycloak 成功/组织失败、组织成功/会话撤销失败、重复事件和乱序目录同步。

## 已考虑的方案

### CRM 自建账号与第三方绑定表

会形成第二认证事实源并恢复历史 `bind_ticket` 风险，因此不采用。

### 使用 Keycloak Group 表示人员和任职

无法可靠表达 Employment、多个有效期 Assignment 和历史责任，也会把组织模型绑定到身份产品，因此不采用。

### 根据手机号或邮箱自动合并

操作方便但存在串号和账号接管风险，且字段权威来源尚未确认，因此不采用。

### Keycloak 管认证，组织模块管人员关联

边界清晰，支持历史、失败关闭和未来更换目录来源，因此采用。

## 影响

- 主体解析需要跨 `auth-context` 与 `organization` 的公开契约，但不能跨表查询。
- Employment 关闭必须同步考虑会话和授权缓存失效，并通过请求时校验兜底。
- 企微联合身份和通讯录同步需要两套职责明确的适配边界。
- 内部关联规则已确认不代表企微应用、SPI、回调域名或自动同步已经实施。

- Keycloak 用户禁用、重新启用、账号恢复和全部 Employment 失效后的公司级策略。
- 管理员代解绑是否需要审批及对应权限。
- 企微应用配置、Keycloak SPI、通讯录字段所有权、同步频率和失效传播目标。

## 非目标

- 本 ADR 不定义公司部门、岗位、员工编号、人员状态枚举或离职审批流程。
- 本 ADR 不定义外部端主体、微信账号关联或外部账号恢复。
- 本 ADR 不创建数据库字段、OpenAPI 端点、Keycloak 配置或企微适配器实现。
- 本 ADR 不确认企微免密登录已经进入第一阶段交付。
