# ADR-0011：PostgreSQL 与 Drizzle 数据持久化基线

- 状态：已接受
- 日期：2026-07-22
- 决策人：项目负责人
- 适用范围：应用数据持久化、模块数据所有权、事务、迁移、测试和数据库访问
- 依赖决策：ADR-0002、ADR-0003、ADR-0010

## 已知事实

- 第一阶段采用 NestJS 模块化单体，并将 API 与 Worker 作为独立运行入口。
- 平台和未来领域模块不得跨模块查询或修改表，跨模块交互必须经过公开接口或契约。
- Transactional Outbox/Inbox 必须与本地状态变更处于同一个数据库事务。
- 组织有效期、授权、任务投影和未来 CRM 数据都需要事务、一致性约束、历史查询和结构化查询。
- 项目负责人确认采用 PostgreSQL、Drizzle ORM，并自研薄数据访问边界、事务协调与迁移治理。

## 允许的假设

- 第一阶段的平台与领域模块可以共享一个应用 PostgreSQL 实例和应用数据库，但在逻辑上按模块隔离。
- PostgreSQL 特有能力可以在模块内部使用，只要其语义经过迁移和集成测试固化。
- Keycloak 和 Flowable 可以部署在同一个 PostgreSQL 实例上以降低早期运维成本，但必须使用独立逻辑数据库和独立凭据。

## 禁止的假设

- 不从历史材料继承 Prisma、具体 PostgreSQL 大版本、业务表、字段、枚举、软删除或 ID 生成方案。
- 不因处于模块化单体就允许跨模块 Join、外键、Repository 复用或直接表访问。
- 不把 Drizzle Schema 或数据库行类型当成 HTTP、事件或 `platform-sdk` 契约。
- 不默认所有迁移都能安全自动回滚，也不把备份替代迁移设计。
- 不在本 ADR 中决定生产数据库拓扑、容量、高可用、备份保留期或灾备指标。

## 决策

### 1. PostgreSQL 使用开源产品，不自研数据库

应用核心关系数据采用 PostgreSQL。选择开源 PostgreSQL 的原因是它提供成熟事务、约束、索引、并发控制、JSONB、全文检索扩展能力、备份恢复和广泛运维生态，能够覆盖 CRM 与公司工作台的长期关系数据需求。自研数据库既没有业务价值，也会引入不可接受的一致性和恢复风险。

具体 PostgreSQL 大版本在部署基线中锁定，并在升级前验证 Drizzle、驱动、Keycloak、Flowable、备份工具和扩展兼容性。开发、CI、预发布和生产必须使用同一大版本系列。

### 2. 使用开源 Drizzle ORM 与 PostgreSQL 驱动

TypeScript 应用使用 Drizzle ORM 进行类型化 Schema、查询和事务，通过经过批准的 PostgreSQL 驱动建立连接。选择 Drizzle 的主要原因：

- 查询和 SQL 映射显式，便于 AI 和人工审查实际执行行为。
- TypeScript Schema 可按模块拆分，减少单一全局模型文件造成的并行开发冲突。
- 不隐藏 PostgreSQL 事务和查询能力；Outbox 抢占、行锁、部分索引等场景可以在模块内部使用受控 SQL。
- 类型安全属于实现辅助，不会强迫 API 或领域契约绑定 ORM 生成类型。

Drizzle 和驱动均使用开源包，项目不 Fork 其源码。具体包版本在工程初始化时锁定，并由依赖升级流程管理。

### 3. 自研薄数据访问与事务边界

`packages/database` 自研以下薄基础设施：

- PostgreSQL 连接池、配置验证、健康检查和可观测性接入。
- 明确的事务运行器或 Unit of Work。
- Drizzle 迁移执行与测试辅助。
- 少量稳定的数据库基础类型和错误映射。

它不得包含组织、授权、客户或其他模块的表定义，不提供跨模块查询服务，也不建设万能 Base Repository。

每个拥有数据的模块在其内部保存 Drizzle Schema、Repository、查询实现和映射器。模块公开接口只返回领域模型或契约模型，不导出 Drizzle 表对象、SQL 片段、查询构造器、数据库行类型或底层事务句柄。

选择自研这一薄层的原因是模块所有权、事务语义、错误码、审计和可观测性属于本项目约束；使用通用 ORM 不能自动建立这些边界。自研范围只包围开源能力，不重复实现 ORM、连接池或迁移引擎。

### 4. 按模块划分数据所有权

- 应用数据库使用明确命名的 PostgreSQL Schema 划分平台模块和未来领域模块的数据区域。
- 表、索引、约束、序列、迁移和 Repository 只有一个所有模块。
- 模块内可以使用外键和事务约束；不同模块的表之间不创建外键，不直接 Join，也不通过数据库 View、Trigger 或存储过程形成隐式耦合。
- 跨模块只保存对方的稳定标识。需要展示或查询组合数据时，通过公开接口、事件驱动的本地投影或应用层编排完成。
- 跨模块投影的数据是副本，必须记录来源标识、来源版本和更新时间，并提供重建或对账方式。

Schema 隔离用于表达所有权，不等于第一阶段拆分微服务。运行时数据库角色仍遵循最小权限；代码依赖检查和集成测试共同防止单进程凭据被用于越界访问。

### 5. 事务边界与 Outbox/Inbox

- 普通写操作只修改一个所有模块的状态。
- 跨模块业务流程通过同步公开命令或异步事件编排，不依赖一个横跨多个模块写模型的“大事务”。
- `eventing-outbox` 拥有应用数据库中的 Outbox/Inbox 基础设施表。业务模块不能直接访问这些表，只能调用正式事务参与接口。
- 本地状态变更与 Outbox 追加由 Unit of Work 在同一个 PostgreSQL 事务中提交。
- 消费者本地状态变更与 Inbox 完成记录也在同一个 PostgreSQL 事务中提交，提交成功后才能确认 RabbitMQ 消息。
- Outbox/Inbox 是允许加入模块本地事务的通用基础设施记录，不因此允许其他平台或领域模块互相写表。
- 涉及 Flowable、Keycloak、对象存储或外部 API 时，不使用数据库事务包装远程调用；采用幂等请求、可恢复状态、重试和对账。

### 6. PostgreSQL、Keycloak 与 Flowable 隔离

- 应用数据、Keycloak 数据和 Flowable 数据使用独立逻辑数据库、独立数据库账号和独立迁移生命周期。
- 三者早期可以共享 PostgreSQL 服务器实例，但任何应用代码不得查询 Keycloak 或 Flowable 数据库。
- Keycloak 数据只由 Keycloak 管理，Flowable 数据只由 Flowable 管理；项目通过协议、Facade 和适配器交互。
- 备份、恢复和版本升级必须分别验证，不能假定恢复其中一个数据库就能恢复完整跨系统状态；跨系统漂移由对账流程处理。

### 7. 迁移采用版本化 SQL 和人工评审

- Drizzle TypeScript Schema 是实现源之一；实际执行的 SQL 迁移文件必须生成或编写后进入仓库，接受代码评审和 CI 校验。
- 已在任何共享环境执行的迁移不可修改或重排，修正必须追加新迁移。
- 应用启动不自动执行迁移；部署使用单独迁移步骤和专用迁移凭据，运行时凭据不拥有 DDL 权限。
- 禁止在共享测试、预发布和生产使用 `drizzle-kit push` 或等价自动同步 Schema。临时本地数据库也优先从正式迁移重建，以尽早发现漂移。
- 迁移按全仓唯一顺序执行，同时记录模块 Owner。执行器使用 PostgreSQL Advisory Lock 或等价机制阻止多个部署并发迁移。
- 数据回填与结构迁移分离。大数据回填必须可恢复、可限速、可观测且幂等，不能长期锁表。
- 生产变更优先采用 Expand/Migrate/Contract：先增加兼容结构，再迁移和双读/双写或切换，确认旧版本不再使用后才删除旧结构。
- 破坏性或不可逆迁移必须有显式批准、影响评估、备份或快照点、恢复演练和前滚修复方案。删除表、列或收紧约束不能与首次替换代码在同一不兼容部署中完成。

“可逆迁移指导”不等于盲目执行 Down Migration。已经产生新数据时，机械回滚 DDL 可能造成二次丢失，生产事故默认优先回滚应用或前滚修复；具体策略由每个迁移说明。

### 8. 查询、安全与可观测性

- 所有外部输入使用参数化查询。允许 Raw SQL，但只能位于拥有模块的 Repository 或迁移中，并需要测试和审查。
- 列表查询必须有明确分页和稳定排序；高风险全表扫描、无界批量更新和 N+1 查询应由测试或审查阻止。
- 连接池分别为 API、Worker 和迁移进程设定上限、超时和标识，不能使用默认无限增长策略。
- 运行时、迁移、只读运维和备份使用不同角色；凭据通过配置引用注入，不进入仓库。
- 数据库日志和慢查询诊断不得泄露密码、Token 或不必要的敏感载荷。
- 指标至少覆盖连接池等待、事务时长、查询延迟、错误/超时/死锁、迁移状态、复制与备份状态；慢查询必须能够关联应用 Trace。

## 测试要求

- Repository 和事务行为使用真实 PostgreSQL 集成测试，不以纯 Mock 代替锁、约束、隔离级别和 SQL 行为验证。
- CI 必须能从空数据库执行全部迁移，并校验 Drizzle Schema 与迁移结果无未声明漂移。
- 迁移测试覆盖当前生产基线到目标版本，而不仅覆盖全新建库。
- 并发测试覆盖唯一约束、乐观或悲观并发控制、Outbox 抢占、Inbox 去重和死锁重试边界。
- 跨模块依赖检查阻止导入其他模块的 Drizzle Schema 或 Repository。
- 破坏性迁移在接近真实数据量的环境验证锁等待、执行时间、应用版本兼容和恢复步骤。

## 已考虑的方案

### Prisma

生态成熟、生成客户端易用，但全局 Schema 和较高抽象层会增加模块并行编辑冲突；复杂 PostgreSQL 锁、索引与 Outbox 查询仍常需绕回 Raw SQL。当前项目更重视 SQL 显式性和按模块组织，因此不采用为默认 ORM。

### TypeORM

与 NestJS 集成广泛，但装饰器实体、级联、懒加载和 Schema 同步选项容易形成隐式行为；长期迁移与复杂查询仍需严格额外约束，因此不采用。

### 仅使用 Raw SQL 或查询构造器

最透明，但需要自行维护较多类型映射、Schema 声明和重复样板。项目仍允许模块内部使用经测试的 Raw SQL，但默认通过 Drizzle 获得类型辅助与迁移工具。

### PostgreSQL + Drizzle + 项目薄边界

复用成熟数据库和 ORM，同时保留显式 SQL、模块所有权、可替换 Repository 与项目事务治理，因此采用。

## 影响

- 项目需要维护模块 Schema、Repository、事务运行器、迁移顺序和真实数据库测试设施。
- 不允许跨模块 Join 会增加部分投影和数据同步工作，但能防止共享数据库演变成隐式单体。
- Drizzle 无法替代数据库设计和 SQL 审查，复杂约束、索引与执行计划仍需要工程评审。
- Keycloak、Flowable 和应用数据库分离后需要独立备份、恢复、升级与对账。

## 非目标

- 本 ADR 不定义任何 CRM 表、字段、枚举、索引或查询。
- 本 ADR 不决定缓存策略、搜索引擎、分析仓库或报表技术。
- 本 ADR 不允许通过建立“通用数据模块”绕过领域所有权。
- 本 ADR 不要求第一阶段把每个模块拆成独立数据库或微服务。
