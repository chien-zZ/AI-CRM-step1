# ADR-0015：第一阶段多客户端应用范围与隔离

- 状态：已接受
- 日期：2026-07-22
- 决策人：项目负责人
- 适用范围：PC Web、内部移动端、外部端及其应用边界
- 依赖决策：ADR-0001、ADR-0003、ADR-0004、ADR-0005、ADR-0006

## 已知事实

- `apps/workbench-web` 已确认为 PC 工作台应用，使用 Vite + React 19 + Ant Design 6 + ProComponents。
- 第三方身份必须通过 Keycloak 联合接入，客户端不能自行签发身份或建立平行账号体系。
- 项目负责人明确要求第一阶段同时创建 PC Web、内部移动端和外部端，不接受只创建 PC Web。
- 内部移动端与外部端的具体载体、UI 技术栈和认证流程在本 ADR 接受时尚未单独确认，后来由 ADR-0016、ADR-0017、ADR-0019 分别确认技术、会话和外部访问模式。

## 允许的假设

- “创建”包含正式应用目录、独立构建/部署边界、业务中立壳层、契约接入和端到端 walking skeleton，而不只是空名字。
- 三个客户端可以复用正式契约、生成 API 客户端和经过证明的无业务基础组件。
- 第一阶段仍不实现未确认的 CRM 领域页面、字段、状态和流程。

## 禁止的假设

- 不把“内部移动端”自动等同于企微 H5、微信小程序、PWA 或原生 App。
- 不把“外部端”自动等同于微信小程序、H5、公众号或面向某类历史材料中的外部人员。
- 不从历史材料继承 Taro、NutUI、Expo、React Native、企微免密或微信登录技术结论。
- 不为了复用代码把内部与外部端合成一个通过隐藏菜单区分的应用。
- 不创建任何 CRM 业务页面或面向未确认用户类型的数据模型。

## 决策

### 1. 第一阶段包含三个正式客户端

- `apps/workbench-web`：公司内部 PC 工作台。
- `apps/internal-mobile`：公司内部移动使用场景的独立客户端入口。
- `apps/external-portal`：面向公司外部用户或合作方场景的独立客户端入口。

三个入口都属于第一阶段范围，必须有各自的应用 Owner、构建、配置、路由、错误边界、健康/版本信息、测试和部署制品。当前先创建业务中立壳层；具体业务能力必须等待领域契约确认。

原生 iOS/Android App 不是由这三个名称自动推导出的第四个客户端。如果内部移动端最终采用原生容器，或外部端需要独立原生 App，必须单独确认构建、签名、分发、升级和推送范围。

### 2. 三个应用保持独立安全边界

- 内部工作台和内部移动端面向内部人员与 Assignment 上下文；外部端采用 ADR-0019 的匿名、邀请或长期登录分级模式，具体外部主体类型仍待业务确认。
- 外部端不得加载内部导航、内部路由表或内部管理组件后仅靠前端隐藏来隔离。
- 每个客户端使用独立 Keycloak Client、回调地址、会话/CORS/CSRF 策略和允许的 API 暴露面；会话传输后来由 ADR-0017 确认，外部匿名/邀请/登录分级由 ADR-0019 确认，具体外部账号关联和恢复仍需另行确认。
- API 在服务端按主体、客户端、受众、权限和数据范围裁决，不能信任前端声明自己是内部端或外部端。
- 外部端默认采用更严格的限流、防枚举、防自动化、输入校验和最小错误披露。

### 3. 应用是组合入口，不拥有业务规则

客户端负责端内路由、布局、交互、缓存和平台能力适配。认证、授权、状态迁移、金额、归属、审批、幂等和数据验证等权威规则仍在服务端模块。

三个应用通过正式 OpenAPI/事件相关契约、生成客户端和 `platform-sdk` 的适用子集访问平台，不深度导入平台或领域实现。移动或外部端的弱网重试不能绕过服务端幂等。

### 4. 复用必须按职责发生

- HTTP 类型与客户端由各自获准的 OpenAPI 暴露面生成，不复制手写 DTO。
- `packages/shared-ui` 只接收已经在至少两个应用中证明语义和交互相同的组件。
- 不恢复历史 `shared-core`；业务规则、页面状态和端专用导航不得因“共享”进入总包。
- 设计 Token、图标、错误语义、Trace/幂等辅助和纯数据契约可以在职责明确的包内复用。
- 内部与外部端即使采用同一开源框架，也必须是独立应用和独立发布制品。

### 5. 每个客户端先交付业务中立 walking skeleton

在业务流程未确认前，每个应用只建设适合其端形态的基础壳层，例如：

- 启动、版本、环境标识、全局错误和不可用状态。
- 认证入口或明确的待接入状态，不伪造已登录用户。
- 当前主体/组织上下文的最小展示边界。
- 受控路由、授权失败、会话过期和退出入口。
- API 客户端、Trace、幂等、文件引用和平台错误处理。
- 至少一个业务中立的只读与一次幂等写入 walking skeleton。

具体通知、任务、文件或表单能力在哪个客户端首阶段展示，按各模块第一阶段范围和端技术确认继续收敛，不因创建应用入口就自动全部复制。

## 自研与开源边界

- 客户端产品、交互、路由组合、安全适配和业务中立壳层由项目自研。
- 构建工具、前端框架、路由、请求、组件库和端运行时使用成熟开源项目，不自研浏览器框架、跨端编译器或原生运行时。
- PC Web 技术栈继续执行 ADR-0001；内部移动端与外部端的开源技术栈在下一项决策中确认。

## 测试要求

- 每个应用独立执行 lint、类型检查、单元测试、构建和端到端冒烟测试。
- 契约测试证明不同客户端只能访问其获准 API 和错误披露范围。
- 安全测试覆盖内部路由/接口不能从外部端访问、客户端标识伪造、会话串用、CORS/CSRF 和对象级越权。
- 跨端 walking skeleton 使用相同业务中立服务端契约，但分别验证弱网、重复提交、会话过期和错误恢复。
- 不以一个客户端的测试通过替代另外两个应用的实际构建与冒烟。

## 已考虑的方案

### 第一阶段只创建 PC Web

范围最小，但项目负责人明确要求内部移动端与外部端同时创建，因此不采用。

### 一个响应式应用服务全部用户

复用最多，但内部与外部身份、API 暴露面、导航、发布和安全威胁不同。通过前端隐藏形成隔离风险过高，因此不采用。

### 三个独立应用入口，共享正式契约

增加构建和测试工作，但安全边界、用户体验与发布节奏清晰，且可在服务端契约层复用核心能力，因此采用。

## 影响

- 第一阶段前端工作从一个应用扩大到三个应用，CI、测试、部署和设计一致性成本显著增加。
- 所有通用契约必须考虑不同端能力，但不能因此降低外部端安全边界。
- 技术栈确认后应提供应用模板和自动化门禁，避免三个 AI 开发任务生成三套不一致的工程规范。
- 客户端均已进入范围不代表企微、微信、原生推送或具体外部用户业务已经确认。

## 后续决策

- 内部移动端与外部端的载体、开源框架、目标制品和不采用原生 App已由 ADR-0016 确认。
- 内部移动端的会话与人员关联已由 ADR-0017、ADR-0018 确认；企微提供商配置和发布方式仍待确认。
- 外部端的会话和访问分级已由 ADR-0017、ADR-0019 确认；具体主体、账号生命周期、首个业务场景、风控供应商、小程序账号和发布方式仍待确认。
- 三端共享设计 Token、API 客户端、端能力适配和测试矩阵。

## 非目标

- 本 ADR 不定义任何移动或外部 CRM 页面、用户类型、字段、权限或业务流程。
- 本 ADR 不确认企微/微信联合登录、消息渠道或小程序审核已经完成。
- 本 ADR 不决定内部移动端与外部端必须使用同一前端框架。
- 本 ADR 不允许客户端成为服务端业务规则的第二事实源。
