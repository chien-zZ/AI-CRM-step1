# ADR-0009：Flowable 审批引擎与职责分离

- 状态：已接受
- 日期：2026-07-22
- 决策人：项目负责人
- 适用范围：`workflow`、`task-center`、领域状态、提醒与调度
- 依赖决策：ADR-0003、ADR-0007、ADR-0008

## 背景

公司工作台未来会出现多种人工审批、条件分支、会签、撤回和流程版本。自研审批表可以覆盖简单顺序审批，但随着流程增加，需要自行解决并发任务、历史实例、版本兼容、流程迁移和操作追踪。

历史材料把审批实例、任务、状态、提醒和业务变更放得较近。若继续混合，Flowable 任务可能被误当成统一待办，BPMN 也可能直接修改领域数据，最终失去模块所有权和故障恢复边界。

## 决策

1. 使用开源 Flowable 作为 BPMN 流程定义、流程版本、流程实例和人工审批任务引擎。
2. `packages/platform-modules/workflow` 提供稳定、业务中立的应用接口，并通过适配器调用 Flowable。领域模块不得直接依赖 Flowable SDK、REST 模型或数据库。
3. Flowable 作为独立运行组件管理自己的数据。任何项目模块不得查询或修改 Flowable 表。
4. BPMN 定义及部署元数据进入仓库并版本化、评审和测试。生产流程不能只在 Flowable 管理界面临时修改。
5. 已启动实例固定使用其启动时的流程定义版本。新版本默认只用于新实例；实例迁移必须有单独方案、回滚指导和人工评审。
6. Flowable 变量只保存流程执行所需的稳定引用、路由输入和必要审批快照，不作为完整业务对象或敏感业务数据的副本。
7. Flowable 不拥有业务状态。订单、客户或其他未来领域对象的状态及合法迁移仍由拥有该数据的领域模块裁决。
8. 审批完成只能通过正式命令或传输无关事件请求领域模块执行动作。领域模块必须重新校验当前状态、权限、版本和幂等，Flowable 不直接更新业务表。
9. `task-center` 维护来自 Flowable 和未来业务系统的统一待办投影。Flowable 是审批任务事实源，领域模块是业务事实源，Task Center 不是二者的替代数据库。
10. 提醒、SLA、催办、升级通知和后台重试是独立关注点，不因为 Flowable 支持 Timer 就全部写入 BPMN。每项时效规则由其所有模块声明，由调度与通知能力执行。
11. Flowable 与业务数据库之间不假设分布式事务。跨边界操作使用幂等命令、Outbox/Inbox 或等价可靠交付、状态对账和可恢复失败流程。
12. Flowable 中的候选人和办理人使用正式主体、Assignment 或受控组织引用，不使用显示姓名作为稳定标识。具体分配规则等待组织与审批业务确认。

## 职责分离

| 关注点 | 事实源或所有者 |
|---|---|
| BPMN 定义、版本、实例和人工审批任务 | Flowable，经 `workflow` 访问 |
| 审批动作授权与数据范围 | `authorization` |
| 人员、组织、岗位和有效任职 | `organization` |
| 业务对象状态与合法迁移 | 对应领域模块 |
| 跨来源统一待办列表 | `task-center` 投影 |
| 提醒、SLA、催办与外部触达 | 调度与 `notifications` |
| 审批和业务动作留痕 | `audit` 及各事实源历史 |
| 表单定义与渲染 | `form-schema` 或对应领域模块 |

## Workflow 公开能力方向

在契约确认后，Workflow Facade 可以提供：

- 部署和查询流程定义及版本。
- 使用幂等键启动流程实例。
- 查询实例状态和当前人工任务。
- 认领、释放、完成、驳回、撤回或取消受支持的任务与实例动作。
- 发布传输无关的流程和任务生命周期事件。
- 触发并查询对账或恢复操作。

实际支持哪些动作由流程契约声明；不能因为 Flowable API 存在某项能力就自动向所有业务开放。

## Task Center 投影原则

- 每条投影记录带来源类型、来源任务标识、版本、受理人或候选范围、状态、截止时间和安全深链引用。
- 来源事件可能重复、乱序或延迟，投影更新必须幂等并处理版本。
- 在 Task Center 点击“完成”时，命令路由回原事实源；Task Center 不能绕过 Workflow 或领域模块自行结束工作。
- 投影缺失或漂移时通过可重放事件或对账任务修复。
- 投影查询仍需授权和数据范围，不能因为数据是副本就扩大可见性。

## 安全、失败与审计

- 启动、认领、完成、驳回、撤回和取消必须在服务端授权并审计。
- 重复启动或重复完成使用幂等键返回稳定结果，不能生成重复实例或重复业务动作。
- Flowable 不可用时，新的流程动作失败并可重试，不能伪造审批成功；已存在业务状态保持不变。
- 业务动作成功但流程回写失败，或流程完成但业务动作失败时，必须进入可观测的待协调状态并由对账恢复。
- 日志和流程变量不得包含密码、Token、非必要敏感字段或完整附件内容。
- 流程定义部署、挂起、恢复和迁移属于高风险管理动作，需要权限、审计和可回滚发布记录。

## 测试要求

- 契约测试隔离 Flowable REST/SDK 模型与 `workflow` 公共接口。
- 集成测试覆盖启动、人工任务、驳回、取消、重复命令、超时、Flowable 不可用和跨边界部分失败。
- BPMN 定义需要静态校验和关键路径测试，版本升级需验证新旧实例并存。
- Task Center 测试覆盖重复、乱序、漏事件、重放、对账和权限过滤。
- 第一阶段仅使用业务无关的审批 walking skeleton，不编码历史材料中的退款、低价或缓考路线。

## 已考虑的方案

### 自研审批引擎

初期代码较少，但需要长期实现 BPMN 等价能力、人工任务并发、版本、历史和迁移，不是项目差异化能力，风险高，因此不采用。

### Flowable 直接侵入领域模块

接入速度看似更快，但会把 Java/Flowable API、任务模型和数据库传播到 NestJS 与领域代码，使替换、测试和故障恢复困难，因此不采用。

### Flowable + 稳定 Workflow Facade

复用成熟流程引擎，通过适配边界保留项目自己的领域状态、任务投影和授权模型，因此采用。

## 影响

- 部署环境增加 Flowable 服务及其数据、健康检查、备份和升级流程。
- 项目需要维护 BPMN 资产、Flowable 适配器、流程事件和对账机制。
- 统一任务中心需要消费多个来源，而不能直接把 Flowable Task 表当作唯一数据源。
- 业务流程确认前只实现业务中立接口和 walking skeleton，不创建具体审批路线。

## 非目标

- 本 ADR 不定义任何实际审批人、条件、会签比例、SLA 或表单字段。
- 本 ADR 不决定 Flowable 的具体版本、数据库或高可用拓扑。
- 本 ADR 不定义未来 CRM 业务状态机。
- 本 ADR 不把所有长流程或后台任务都建模为 BPMN。
