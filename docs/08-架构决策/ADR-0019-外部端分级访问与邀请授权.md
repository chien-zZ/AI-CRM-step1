# ADR-0019：外部端分级访问与邀请授权

- 状态：已接受
- 日期：2026-07-22
- 决策人：项目负责人
- 适用范围：`apps/external-portal`、外部受众 HTTP 契约、`authorization`、认证与未来业务模块
- 依赖决策：ADR-0004、ADR-0006、ADR-0007、ADR-0015、ADR-0016、ADR-0017

## 已知事实

- 外部端是独立 Taro 应用，输出 H5 与微信小程序，并只消费外部 Allowlist OpenAPI。
- Keycloak 是唯一身份提供商；H5 与微信小程序的长期登录会话边界已由 ADR-0017 确认。
- 具体外部主体可能是客户、合作方、渠道人员或临时提交者，但这些业务类型尚未确认。
- 历史材料提出外部快速提交，但不能据此确认匿名表单、用户字段、账号体系或业务流程。

## 允许的假设

- 某些未来外部流程可能不需要长期账号，也可能只需要对单个资源执行一次限定操作。
- 外部接口需要比内部接口更严格的限流、防枚举、防自动化、输入校验和错误最小披露。
- 业务模块确认具体流程后，可以请求业务中立的短期邀请凭据能力，而不自行实现 Token。

## 禁止的假设

- 不创建通用 `ExternalUser`、`Partner`、`CustomerAccount` 或其他含义不明的外部主体模型。
- 不因为外部端存在，就默认所有外部访问必须注册、登录或绑定微信。
- 不把邀请凭据视为身份凭证，不从凭据推断持有人姓名、账号或业务关系。
- 不允许匿名、邀请或登录模式自动互相升级权限。
- 不从历史材料创建匿名提交端点、邀请表、外部账号表、字段或业务权限。

## 决策

### 1. 外部端支持三种明确分离的访问模式

| 模式 | 表达的事实 | 适用方向 | 不表达的事实 |
|---|---|---|---|
| 匿名访问 | 未认证请求可调用明确公开的端点 | 无需识别人的公开查询或提交 | 不知道访问者是谁 |
| 邀请授权 | 持有人可在限定时间内执行限定资源动作 | 一次办理、补充资料、确认或查看限定内容 | 不证明持有人身份 |
| 长期登录 | Keycloak 已认证一个稳定主体 | 重复办理、持续查看记录、维护资料 | 不自动证明任何业务关系或权限 |

每个 HTTP 操作必须在契约中显式声明允许的模式。未声明时默认要求已认证且经服务端授权，不能由前端根据页面入口猜测。

### 2. 匿名访问是显式能力，不是认证失败的降级

- 只有业务模块明确批准为公开的外部端点才能匿名访问；内部端点和未分类端点默认拒绝。
- 会话过期、Keycloak 故障、邀请凭据无效或授权失败时，不能降级为匿名继续原操作。
- 匿名请求仍执行请求大小、内容类型、Schema、幂等、速率、自动化风险和滥用控制。
- 错误不得泄露资源是否存在、账号是否存在、内部状态、人员信息或可用于枚举的差异。
- 是否需要验证码、行为验证或人工复核由具体业务风险决定，不在本 ADR 中选定供应商。

### 3. 邀请授权是受限能力凭据，不是外部账号

邀请凭据必须绑定经评审的最小授权边界：

- 由哪个拥有模块发起。
- 允许的资源类型、资源引用和动作集合。
- 外部受众与适用客户端/制品。
- 生效时间、绝对到期时间和最大使用次数。
- 撤销、已消费、过期和风险冻结状态。
- 发起原因、审计关联和可选的额外校验要求。

邀请凭据不能承载完整业务对象、个人信息、权限集合快照或内部数据库标识。资源当前是否仍存在、状态是否仍允许操作、请求是否幂等以及对象级规则，必须由拥有该资源的模块在每次操作时重新判断。

### 4. 邀请凭据采用服务端状态和随机不透明 Token

- 客户端只获得使用密码学安全随机数生成的高熵不透明 Token。
- 数据库仅保存 Token 的不可逆摘要及必要控制元数据；明文 Token 不进入数据库、日志、Trace、埋点或错误响应。
- 浏览器可通过不会发送给服务器的 URL Fragment 接收 Token，再由客户端以专用请求头兑换；小程序使用经评审的 scene/启动参数交换方案。原始 Token 不得出现在 HTTP 查询/路径、服务器访问日志、第三方 Referer、分析参数或公开缓存中。
- 对高风险或含敏感信息的操作，凭据持有本身不足以放行，业务契约必须增加一次性验证码、已知信息校验或 Keycloak 重新认证。
- 短期、单用途并不等于必须一次读取即失效；最大使用次数和消费时点由实际流程确认，但默认最小化。
- Token 泄露、撤销、过期、超次、受众错误或资源状态改变时失败关闭。

不使用自包含 JWT 邀请凭据作为默认方案。服务端状态便于立即撤销、原子消费、对账和最小化载荷，也避免长期密钥轮换与过期授权快照问题。

### 5. 业务模块与平台薄层职责分离

- 拥有资源的业务模块决定是否允许邀请、允许哪些动作、何时发放以及操作前后的业务不变量。
- 业务中立的外部访问授权薄层负责安全 Token 生成、摘要校验、TTL、使用次数、原子消费、撤销、风险冻结和审计技术信息。
- `authorization` 接收经过验证的访问模式和最小能力上下文，执行默认拒绝及通用决策；它不替业务模块判断资源状态。
- `apps/api` 负责传输适配、外部限流、最小错误披露和安全响应头，不拥有邀请业务规则。
- `external-portal` 只呈现服务端允许的状态，不能解析 Token 推断权限，也不能把邀请信息写入持久化 UI 状态。

在首个真实邀请场景确认前，不创建 `packages/platform-modules/external-access` 或数据表。届时先定义契约，再决定将薄层作为独立平台模块还是由已有安全边界承载；不得把它复制到多个业务模块。

### 6. 长期账号只为稳定、重复关系创建

- 只有真实流程需要跨会话查看记录、重复办理、维护资料或管理授权时，才为已确认的外部主体建立 Keycloak 用户。
- 外部主体业务档案由对应领域模块拥有，Keycloak 用户只表示认证主体；不得创建统一外部业务主表来替代领域模型。
- 外部 H5 使用隔离 BFF HttpOnly Cookie；微信小程序使用 ADR-0017 的不透明服务端会话句柄。
- 微信身份与 Keycloak 用户的关联执行 ADR-0006、ADR-0017 的安全边界，具体首次关联、恢复和业务主体映射等待对应领域确认。
- 邀请访问升级为长期登录时必须显式重新认证和重新授权，原邀请权限不能静默继承到账号。

### 7. 三种模式使用不同的请求上下文

- 匿名上下文只包含请求、安全和追踪所需的最小信息，不伪造主体 ID。
- 邀请上下文只包含经过服务端验证的能力引用、受众和限制，不宣称已认证身份。
- 登录上下文来自 Keycloak 主体和已确认的业务主体关联。
- 同一请求只能选定一个权威访问模式；存在 Cookie 和邀请 Token 时不得合并两者权限取并集。
- 需要从邀请切换到登录模式时，由服务端明确返回重新认证要求并在新请求中重新裁决。

## 自研、开源与托管边界

| 能力 | 选择 | 原因 |
|---|---|---|
| 长期身份、登录和联合身份 | 开源 Keycloak | 不自研密码、Token 和账号恢复基础设施 |
| 邀请 Token 随机生成、摘要与常量时间比较 | Node 标准密码学能力或成熟开源库 | 不自研密码学算法 |
| 邀请授权编排与状态控制 | 项目自研薄层 | 需要与本项目资源引用、审计、幂等和撤销语义结合 |
| 短期速率和风险协调 | 开源 Redis + 自研策略适配 | Redis 适合计数与短期协调，不保存唯一授权事实 |
| 验证码/行为验证 | 暂不选型，经适配器接入开源或托管服务 | 需结合真实流量、合规、可用性和成本再选择 |
| WAF/CDN 边缘防护 | 部署阶段评估托管能力 | 边缘攻击缓解适合托管基础设施，但不能替代应用授权 |

## 事务、幂等与并发

- 邀请创建、撤销、消费和关联审计属于耐久事实，使用 PostgreSQL 和模块自有 Schema；Redis 仅作速率、短期冻结或缓存。
- 单次或限次凭据必须通过数据库条件更新或等价原子机制消费，不能用“先查后改”造成并发超用。
- 业务写入和邀请消费需要明确事务边界。若两者属于同一数据库事务，使用受控 Unit of Work；跨边界时采用预留/确认或可恢复状态，不使用分布式事务。
- 客户端弱网重试必须携带业务幂等键；邀请 Token 本身不兼作幂等键。
- 重复提交返回与首次已提交结果一致的安全语义，不能重复产生业务副作用。

## 授权、审计与隐私

- 创建、查看管理信息、撤销和重发邀请均需要独立权限；不能因能操作业务资源就默认能签发邀请。
- 审计记录邀请引用、拥有模块、资源引用、动作、结果、原因、使用计数、操作者/已认证主体（如有）、风险结果和 Trace ID，不记录明文 Token。
- 匿名和邀请模式按数据最小化原则收集信息；隐私声明、同意、保存期限和删除要求由具体业务数据规则确认。
- 敏感字段、附件下载、导出和资金相关操作不得仅凭通用邀请默认开放，必须单独风险评审。
- 邀请页面设置禁止搜索引擎索引、适当 Referrer Policy、缓存控制和内容安全策略；第三方资源不得获得完整邀请 URL。

## 可观测性与测试

- 指标覆盖匿名请求量/拒绝、邀请创建/兑换/撤销/过期/超次、枚举与限流拒绝、验证码结果和外部依赖错误。
- 结构化日志按访问模式记录稳定结果和 Trace ID，不记录 Token、验证码、个人敏感信息或可还原的资源秘密。
- 契约测试验证每个外部操作只接受声明的访问模式，内部和未分类操作默认拒绝。
- 并发测试覆盖单次 Token 多请求竞争、业务提交重试、撤销与消费竞态、过期边界和 Redis 丢失。
- 安全测试覆盖 Token 猜测、泄露到 URL/日志/Referer、资源枚举、错误差异、CSRF（H5）、重放、自动化和登录/邀请权限混用。

## 已考虑的方案

### 所有外部用户先注册登录

身份清晰但增加流程摩擦，并会迫使尚未确认的临时访问者进入一个通用账号模型，因此不采用。

### 所有外部操作匿名开放

体验简单但无法安全支持定向查看、补充和确认，也难以撤销授权，因此不采用。

### 自包含 JWT 邀请

可减少数据库读取，但撤销、限次、原子消费和资源状态变化处理更复杂，且容易把过多信息塞进 Token，因此不作为默认方案。

### 匿名、邀请、长期登录分级

能按实际风险选择最小身份强度，避免提前创建外部账号模型，同时保持明确授权边界，因此采用。

## 影响

- 外部 OpenAPI 需要为每个操作声明受众和允许的访问模式，生成客户端不能因此包含内部接口。
- `authorization` 和错误契约需要区分匿名、邀请无效/过期和登录不足，但对终端继续最小披露。
- 未来每个邀请场景都必须由业务 Owner 确认资源、动作、有效期、次数、撤销和附加验证，不能只复用“万能邀请链接”。
- 外部端身份模式已确认不代表任何匿名业务流程、邀请流程或外部账号已经进入第一阶段交付。

## 待后续决策

- 该场景使用匿名、邀请还是长期登录，以及是否需要附加验证。
- 邀请凭据具体有效期、次数、传输方式、风险等级和恢复体验。
- 微信外部身份首次关联、解绑、恢复和业务主体映射。
- 验证码/行为验证、WAF/CDN、隐私同意和数据保留选型。

## 非目标

- 本 ADR 不定义客户、合作方、渠道、学生或其他外部主体。
- 本 ADR 不创建匿名提交接口、邀请契约、邀请表、平台模块或 Keycloak 外部用户。
- 本 ADR 不允许匿名或邀请访问内部 API、内部导航或管理功能。
- 本 ADR 不确认外部端第一阶段必须交付任何具体业务表单。
