# ADR-0025：授权策略持久化与发布边界

- 状态：已接受
- 日期：2026-07-27
- 接受日期：2026-07-28
- 决策人：项目负责人
- 适用范围：`packages/platform-modules/authorization` 的生产持久化适配器、发布流程、决策审计与 Redis 缓存失效
- 依赖决策：ADR-0003、ADR-0007、ADR-0018、ADR-0021、ADR-0022、ADR-0023

## 背景

ADR-0007 已确定自研轻量业务授权核心及默认拒绝原则。IAM-03 已交付稳定的策略存储、授权决策记录和可选缓存端口，但有意没有选择生产数据库结构与发布流程。当前生产组合因此不能把内存或 Redis 中的数据当成授权事实，也不能在没有可验证策略和耐久决策记录时宣称就绪。

本 ADR 只决定持久化与发布的不变量，使后续数据库 migration、repository、发布用例和运行期组合可以分别实现和复核。它不提供真实 Permission、Role 或 Grant，也不确认权限管理员与审批路线。ADR 的接受不构成生产 schema、migration 或生产授权链路已经实现的声明；这些工作仍须独立立项、评审和验收。

## 决策

### 1. Schema Owner 与访问边界

1. `authorization` 是授权策略、策略发布记录和授权决策记录的唯一能力 Owner，并拥有独立的 PostgreSQL schema。具体 schema/table/column 名称由后续 migration 任务决定，本 ADR 不预先固定物理结构。
2. 策略持久化至少在逻辑上区分：不可变策略版本内容、当前发布选择、发布历史和授权决策记录。是否规范化存储或保存经校验的规范化文档，由实现评审决定；任一方案都必须能按版本完整、确定地重建现有 `AuthorizationPolicySnapshot`。
3. 只有 `authorization` 自有 repository 可以读写该 schema。应用通过现有 `AuthorizationPolicyStore`、`AuthorizationDecisionRecorder` 和授权服务公共入口访问；其他模块不得直接查表或取得数据库事务句柄。
4. `organization` 仍拥有人、组织、岗位和任职事实。策略只能保存现有合同允许的稳定 Workforce Person/Assignment 引用，不复制或推断组织事实。Keycloak Claim、Role 或 Token 不是策略持久化事实。
5. Redis、技术日志、指标、Trace、Sentry 和前端状态均不是策略或决策审计事实源。

### 2. 不可变策略版本与发布

1. 每个可发布版本包含完整的 Permission 声明、Role 权限集合和 Grant 集合，并带有唯一的有界版本标识、策略契约版本及内容摘要。版本标识一旦绑定内容便永久不可复用；相同标识和不同内容必须拒绝。
2. 已发布版本及其内容不可修改、补写或删除后重建。更正只能创建新版本。历史版本至少保留到审计、兼容与恢复规则允许清理为止；清理规则另行评审，不能由普通发布流程隐式执行。
3. 发布前必须完成：合同与运行期校验、引用完整性校验、时间区间校验、规范化内容摘要校验、空策略检查和目标版本可完整回读校验。任一检查失败时不得改变当前版本。
4. 版本内容写入、发布记录追加和当前版本指针切换必须在单一 PostgreSQL 事务中完成，并使用并发控制避免丢失更新。同一发布意图的安全重试只能得到同一结果；并发发布必须有且只有一个明确顺序，不得让读取者观察到部分快照。
5. `AuthorizationPolicyStore.currentVersion()` 只返回已提交的当前版本，`load(version)` 只返回与该标识及摘要一致的完整不可变快照。读到缺失、未发布、摘要不符或无法解析的内容时失败关闭。
6. 第一阶段不引入定时发布、多环境自动提升或通用策略编排器。发布权限、复核/审批路线和紧急发布责任人未确认前，不得暴露可供生产使用的写接口。

### 3. Permission、Role 与 Grant 的有效期语义

1. Permission 声明和 Role 定义的生效边界由“当前发布版本”决定：它们只在包含它们的版本被选为当前版本期间参与裁决。移除或更正必须通过新版本完成，不给已发布 Permission 或 Role 原地增加状态或覆盖内容。
2. Permission code 的含义在版本间必须稳定。若资源、动作或数据范围维度的语义发生不兼容变化，应使用新的 Permission code 或新的契约版本；不得在旧 code 下静默扩大访问。
3. Role 是版本内不可变的 Permission/Scope 集合，不是岗位名称。相同 Role ID 在后续版本出现时，其内容以该完整版本为准；变更必须可通过发布历史审计，不能绕过版本发布单独生效。
4. Grant 除受当前版本边界约束外，还使用已有的半开有效区间 `[validFrom, validTo)`。`validTo` 缺失只表示开放结束时间，不表示不可撤销；撤销或缩短有效期必须发布新版本，历史记录保持不变。
5. Assignment Grant 仅在该 Assignment 由调用方明确选中且 `auth-context` 确认为当前有效时适用；不得合并并行 Assignment。Workforce Person Grant 仍是显式受控例外，不能由姓名、联系方式、Position 或 Keycloak 数据推断。
6. 当前合同尚未给 Permission/Role 增加独立日历时间字段，因此本 ADR 不发明这些字段。若未来业务确认需要独立于发布版本的时间窗口，应先变更权限契约并完成兼容评审。

### 4. 授权决策审计

1. 每次 `check`、批量中的每个单项检查、`requireAllowed` 和 `resolveDataScope` 都必须通过现有必需的 `AuthorizationDecisionRecorder` 耐久记录后，结果才可返回。记录失败、超时或无法确认提交时，裁决服务失败关闭；不得因原计算为 allow 而放行。
2. 决策记录是追加型事实，使用全局唯一 `decisionId` 去重。Recorder 对同一 `decisionId` 与相同内容的重试必须幂等；同一 ID 的冲突内容必须拒绝并告警。业务命令的事务与授权决策记录是不同事实，不得声称二者自动形成分布式原子事务。
3. 最小记录范围沿用公共接口：决策 ID、裁决时间、操作种类、Resource、Action/Permission code、allow/deny、稳定原因、策略版本、Workforce Person（存在有效主体时）、明确选择的 Assignment（如有）和安全 W3C Trace 引用。不得保存 Token、Cookie、Secret、请求/响应体、原始 Claim、任意资源对象内容、SQL 参数或原始 Provider payload。
4. 决策记录属于授权证据，不替代拥有模块的业务审计，也不进入普通技术日志。高风险业务动作仍由 `audit` 能力记录其业务审计事实，并通过安全引用关联授权决策；模块间不得互查表。
5. 在风险分级和保留规则被负责人接受前，生产适配器不得抽样丢弃授权决策。精确保留期限、归档与合法清除流程仍是未决治理项，后续决定不得修改既有决策事实。

### 5. Redis 缓存与失效

1. PostgreSQL 中的当前发布选择与不可变策略版本是权威事实。Redis 只缓存经权威快照计算并验证的评估材料，不缓存可独立授权的 Grant 真值。
2. 缓存命名空间和键必须包含环境隔离及策略版本摘要；键和值不得泄露 Workforce Person、Assignment、Scope 值或资源对象事实。TTL 必须有界，且不得越过 Grant 的下一个有效期边界。
3. 发布事务提交后，发布用例请求清理旧版本缓存。失效是幂等的清理动作，可安全重试；清理消息丢失或 Redis 不可用不能使旧值适用于新版本，因为运行期每次先从权威存储取得当前版本，且跨版本键永不复用。
4. 当前版本切换后，不允许因缓存命中、失效延迟或 Redis 故障回退到旧策略。缓存 miss、内容损坏或操作失败时，应基于已验证的当前权威快照重新计算；若权威快照不可用则失败关闭。
5. 具体 Redis TTL、容量、失效投递机制和告警阈值是后续运行配置/实现决定。不得为缓存失效另建第二套业务消息真值或绕过既有 Outbox/RabbitMQ/Inbox 边界。

### 6. 空策略、启动与 Readiness

1. 没有当前发布版本、当前版本无法完整加载，或当前版本的 Permission、Role、Grant 任一集合为空，都视为不可发布/不可就绪的生产授权策略。生产发布和 Readiness 必须失败关闭。
2. 运行期不得用内置超级用户、默认 allow、Keycloak Role、测试 fixture、上次进程内快照或 Redis 残留代替权威当前版本。策略错误对外只返回稳定的拒绝/不可用语义，不暴露内部内容或资源是否存在。
3. 首次生产启用必须通过同一受审发布流程建立非空、可验证的基线版本。首发使用受审平台权限目录、一个明确选中的当前有效 Assignment 以及版本化完整快照；真实 Assignment/操作者映射必须来自生产 Organization 与发布证据，仓库不得提供替代值。
4. 本条不要求虚构“全员默认角色”来满足非空检查，也不允许应用启动、migration 或测试 Factory 自动注入基线内容。

### 7. Migration、兼容与恢复

1. 后续物理 schema 只能通过经审核、版本化的 Drizzle SQL migration 创建或改变。禁止应用启动自动建表、自动 schema 同步和 `drizzle-kit push`；migration 必须包含前向、回退或前向修复指导及备份/恢复验证步骤。
2. 数据结构升级采用 expand–migrate–contract：先增加向后兼容结构，再回填并校验，切换读写后才能在独立 migration 中收缩。旧应用与新应用的共存窗口必须在 migration 说明中明确；不能兼容时必须使用停机窗口并保持授权失败关闭。
3. 每个持久版本记录其策略契约版本。Reader 至少严格支持当前已接受的 v1；遇到未知契约版本不得猜测或降级解释。契约升级必须先更新合同，再提供确定性转换/双读策略和固定兼容测试。
4. 部署回退不得覆盖策略内容或把数据库回退到无法读取当前策略的应用版本。应用回退前必须验证其能读取当前 schema 与策略契约，否则停止回退并保持服务不可用，而不是扩大权限。
5. 逻辑恢复通过追加一条恢复发布记录，把当前选择重新指向一个仍保留、摘要校验通过且与运行期兼容的不可变历史版本；历史版本本身不得修改。恢复提交后按正常发布流程触发缓存清理并记录操作者/原因的管理审计。
6. PostgreSQL 备份必须离开两台服务器故障域，Secret 仍遵守 ADR-0023。恢复演练必须验证版本内容、当前指针、发布历史、决策记录与摘要一致性。本 ADR 不宣称自动故障转移、SLA、RPO 或 RTO。

## 失败与并发行为摘要

| 场景 | 必需行为 |
|---|---|
| 无当前版本、空策略或损坏快照 | 拒绝发布/Readiness；运行期失败关闭 |
| 发布校验或事务失败 | 当前版本保持不变，不产生部分可见版本 |
| 同版本、同内容重试 | 幂等返回已有结果 |
| 同版本、不同内容 | 拒绝并记录安全告警 |
| 并发发布 | 通过事务并发控制形成单一明确顺序，冲突方重读后重试 |
| Redis 失效失败 | 不回退策略；依靠版本隔离，异步重试清理 |
| 权威策略存储不可用 | 不使用 Redis 独立放行，失败关闭 |
| 决策记录失败或提交结果不确定 | 不返回裁决结果，失败关闭；以 decision ID 安全重试 |
| 回退到历史策略 | 校验后追加恢复发布记录并原子切换，不修改历史内容 |

## 授权与审计边界

- 策略能力 Owner 是 `authorization`；发布结果责任人是项目负责人。策略内容由 Authorization capability Owner 提交，独立 Reviewer 复核，Production Release Operator 执行。提交人与复核人必须不同；实际人员/主体映射写入当次受控发布证据，不在仓库虚构姓名或 UUID。
- 普通发布必须有项目负责人批准；执行人只能在受保护发布环境中调用完整快照发布命令，不获得直接改表、跳过审计或覆盖历史的权限。首发必须带 `expectedPreviousVersion: null`；后续发布/恢复必须带精确当前版本，事务内不匹配即拒绝。
- 紧急路线仍由项目负责人批准并至少一名非执行 Reviewer 复核；只能发布新的完整版本或重新指向已验证的不可变历史版本，不能直改 Grant、关闭审计或使用默认 allow。事后复核、访问回收和事故记录为必需证据。
- 所有管理变更必须进入管理审计；普通授权决策进入授权决策记录。两者不能用 Pino/Sentry/Trace 替代。
- 策略发布前后的业务操作仍必须由服务端调用授权接口。前端按钮隐藏、客户端缓存或路由保护不能替代服务端裁决。

## 影响

- `authorization` 后续需要自有 PostgreSQL repository、版本化 migration、事务性发布用例、耐久决策 Recorder 和应用组合适配器。
- 生产 API 在权威非空策略和必需决策 Recorder 均未闭合前继续失败关闭，这是本决策的安全结果。
- 不可变完整快照会增加存储，但降低部分快照、原地修改和恢复歧义；后续可在不改变公共接口的前提下选择规范化或文档化物理表示。
- 每次发布都形成新版本，Role/Grant 变更不会直接更新当前事实。缓存失效只影响性能和清理，不影响授权正确性。

## 兼容性

- 现有 `AuthorizationPolicyStore.currentVersion()` / `load(version)`、`AuthorizationDecisionRecorder.record(...)`、`invalidatePolicyVersion(version)` 和 SDK 授权入口保持不变。
- 现有 v1 策略快照继续是运行期边界；本 ADR 增加持久化与发布不变量，不向公共契约添加字段。
- 未来若需要发布管理合同、独立 Permission/Role 时间窗或新的策略契约版本，必须合同先行并独立评审。

## 非目标

- 不在仓库定义真人姓名、生产 Workforce Person/Assignment UUID、Scope 业务值或组织模型；这些值只能来自当次正式发布证据。
- 不创建数据库 schema、migration、repository、发布 API/UI、缓存消费者或生产适配器。
- 不引入 Casbin、OpenFGA、OPA、Cerbos、通用表达式语言或关系授权图。
- 不确定生产 Redis 参数、审计保留期限、归档介质、SLA、RPO、RTO 或高可用拓扑。
- 不改变 Keycloak、`organization`、`audit` 或任何业务模块的数据所有权。

## 接受记录与后续工作

项目负责人于 2026-07-28 接受本 ADR，确认 `authorization` 的 schema ownership、非空生产策略要求、所有决策耐久记录的阶段性要求，以及恢复指向历史版本的方式。接受后仍需分别立项并 Review：

1. 物理数据模型与可逆 Drizzle SQL migration。
2. 事务性 repository、发布用例和并发/幂等测试。
3. 生产 Decision Recorder、保留/归档规则与审计联调。
4. Redis 失效重试实现、运行参数和故障测试。
5. 在生产 Organization 中确认项目负责人、提交人、独立复核人与执行人的真实主体/Assignment 映射，并保存不含个人资料或凭据的发布证据。

在这些工作完成且 `pnpm check` 与 Walking Skeleton 验收证据通过前，本 ADR 的接受不得被解释为生产授权链路已经完成。

2026-07-29，项目负责人通过 G3 生产组合指令补充确认上述角色责任、职责分离、普通/紧急路线和管理审计要求。该确认不授权仓库虚构实际人员或生产 Assignment，也不等于首发已经在真实 PostgreSQL 中提交。
